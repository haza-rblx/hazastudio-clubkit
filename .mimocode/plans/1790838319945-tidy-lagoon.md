## 2. Cara Kerja — INIFIX (sederhana, client-only)

**Deteksi idle:**
- Pakai `os.time()` + polling manual setiap 5 detik
- Reset `lastInputTime` pada event:
  - `UserInputService.InputBegan`
  - `UserInputService.InputChanged`
  - `UserInputService.TouchTapInWorld`
  - `UserInputService.WindowFocused`
- Tambahan: loop 5 detik cek posisi mouse (`GetMouseLocation`) — kalau berubah, reset timer
- **Tunggu sampai `Players.LocalPlayer:GetAttribute("IsLoading") ~= false`** sebelum mulai (gating loading)

**Threshold:** `AFK_TIMEOUT = 15 * 60` (15 menit, hardcoded)

**Trigger rejoin:** setelah idle >= 15 menit:
- Set `isRejoining = true` (stop loop check)
- Ambil `HumanoidRootPart.Position` (X, Y, Z)
- Baca attribute `SyncingTo` dari character (untuk sync info)
- `FireServer(AFKRejoinRemote, { Position = {x,y,z}, SyncingTo = ... })`
- Tidak ada response handler, tidak ada retry, tidak ada notifikasi

**Cleanup:** `AFKController.Destroy()` → `isRejoining = true` + `_maid:Destroy()`

**Kelebihan inifix (hal-hal yang mungkin menarik untuk thebasic):**
1. **Mouse movement polling loop** (cek `GetMouseLocation` tiap 5 detik) — inifix punya ini, thebasic TIDAK (thebasic cuma InputChanged, dan bilang "InputBegan misses mouse movement"). Wait — thebasic juga wire `InputChanged`, jadi sebenarnya thebasic juga tangkap mouse movement. Tapi thebasic bilang "input-event-based resets alone leak stale state across streaks" dan andalkan `Player.Idled` idleTime regression sebagai authoritative reset.
2. **`TouchTapInWorld` event** — inifix explicitly handle touch tap; thebasic tidak (thebasic pakai InputBegan + InputChanged yang mungkin tidak cover touch di mobile dengan baik).
3. **`WindowFocused` explicit handling** — inifix handle window focus sebagai reset; thebasic tidak punya handler WindowFocusReleased/WindowFocused (cuma InputBegan/InputChanged).
4. **Wait for `IsLoading` attribute** — inifix menunda mulai AFK detection sampai loading selesai. thebasic tidak punya gating seperti ini (langsung init di `init(deps)`).
5. **`Maid` pattern** — inifix pakai Maid untuk cleanup koneksi; thebasic pakai manual `_connections` table + loop disconnect. Bukan perbedaan behavior tapi organisasi kode.
6. **Position payload sederhana** `{x,y,z}` — inifix kirim posisi sederhana; thebasic kirim `reportedIdleSec + cycleId + stepIndex` (lebih kaya metadata).

**Kekurangan inifix:**
- Tidak ada server-side validation/rate-limit (client bisa spam FireServer)
- Tidak ada retry/escalation ladder (1 attempt, done)
- Tidak ada position restore setelah rejoin (server-side handler tidak restore posisi — atau unknown karena handler tidak ditemukan)
- Tidak ada sync dance restore (cuma kirim `SyncingTo` attribute value, tapi tidak restore)
- Tidak ada notifikasi warning sebelum rejoin
- Tidak ada teleport confirm/timeout handling
- Tidak ada handling `TeleportInitFailed`
- Threshold 15 menit hardcoded, tidak config-driven
- Tidak ada cycle id / dedup request

## 3. Cara Kerja — THEBASIC (sophisticated, server-authoritative)

### Client (`AfkGuardController`)
- **Sumber idle:** `Players.LocalPlayer.Idled` event (engine-authoritative, fires ~129s pertama, lalu tiap 30s, `idleTime` = detik asli sejak input terakhir)
- **Reset cycle:** deteksi `idleTime` regression (drop > 1s) = engine restart idle streak → reset `cycle` state. Lebih reliable dari input events.
- **Input event reset (fast-path):** `InputBegan` + `InputChanged` → `resetIdleState()` (idempotent, allocation-free)
- **Warn threshold:** `idleTime >= IDLE_WARN_SEC (120s)` → tampilkan notifikasi warning sekali
- **Escalation ladder (`resolveLadderStep`):** pilih rung tertinggi yang idle time-nya sudah lewat & belum fired. Mark fired sebelum FireServer. Response handler un-fire rung kalau `isTransientDenial(outcome)`.
- **Request payload:** `{ requestId (GUID), reportedIdleSec, cycleId (GUID), stepIndex }`
- **Response handler:** `OnClientEvent` → log + un-fire rung kalau transient denial (rate/in-flight/carry)
- **Character respawn reset:** `CharacterAdded` → reset `loggedIdleAfterRespawn` probe
- **Notifications via `NotifService`** dengan `notifySafe` (pcall — notif gagal tidak abort safety path)
- **Feature flag:** `Config.FeatureFlags.AfkGuardEnabled` + `Config.AfkGuard.ENABLED`

### Domain (`AfkGuardDomain`) — pure validation, shared
- `getMinAcceptableIdleSec()` = `IDLE_THRESHOLD_SEC - IDLE_TOLERANCE_SEC` (server validation floor)
- `isWarnThreshold(idleSec)` / `isRejoinThreshold(idleSec)`
- `isTransientDenial(outcome)` → true untuk `denied_rate_limited`, `denied_in_flight`, `denied_carry_active`
- `nextRetryDelaySec(outcome, retryAfterSec)` → backoff + jitter ±10%
- `isBelowTeleportAbortIdle(reportedIdleSec)` → `< 19 * 60` (jaga jangan teleport di kick window)
- `getHardStopIdleSec()` = `19 * 60` (stop past ini)
- `getLadder()` → normalisasi + sort ascending, fallback single rung
- `resolveLadderStep(idleSec, firedSteps)` → pilih rung tertinggi belum fired; return nil past hard stop
- `isIdleRegression(prevIdleSec, idleSec)` → drop > 1s = new streak
- `validateRejoinRequest(raw)` → validasi requestId (<=64 char), cycleId, stepIndex (1..#ladder), reportedIdleSec (range), return `Result`
- `validateSyncRestorePayload(raw)` → validasi sync restore (wasSyncing, animation, speed, dll — strict whitelist field)
- Types: `AfkRejoinRequest`, `LadderStep`, `RejoinOutcome`, `RejoinResponse`, `ClientCycleState`, `SyncRestorePayload`

### Server (`AfkGuardService`) — server-authoritative guard
- **Remote setup:** auto-create `AfkRejoinRequest` + `AfkRejoinResponse` RemoteEvent kalau belum ada
- **Rate limiter:** `RateLimiter.new(AUTO_REJOIN_RATE_MAX=1, AUTO_REJOIN_RATE_WINDOW=900)` — 1 token per 15 menit per player
- **Cycle admission (`admitCycle`):** 1 token = 1 idle cycle (streak). Rung dalam cycle sama reuse token → retry tidak di-starve. TTL cycle = `AUTO_REJOIN_CYCLE_TTL_SEC=600`.
- **Dedup:** `TTLSet` untuk requestId (`processedRequests`)
- **In-flight guard:** `inFlightAfkRejoin[userId]` = timestamp; stale reap setelah `max(confirm, init) + 20`
- **Blocked state:** cek `carryService.getPartnerId(userId)` → deny `denied_carry_active` kalau lagi di-carry
- **Order validasi:** invalid → duplicate → in-flight → carry → rate/cycle → service-available
- **Response outcomes:** `allowed`, `denied_rate_limited`, `denied_in_flight`, `denied_carry_active`, `denied_service_unavailable`, `denied_invalid`, `rejoin_failed`
- **Eksekusi:** panggil `sessionCommandService:handleAfkRejoin(player, reportedIdleSec, sameServer)`
- **`onPlayerRemoving`:** log apakah rejoin confirmed (cycle closed) atau lost player (leak — ladder habis tanpa rejoin)
- **Log metric:** `afk_cycle_lost_player` — untuk bedakan "rejoin berhasil" vs "Roblox idle-kick"

### Teleport execution (`SessionCommandService.handleAfkRejoin`)
- `safeTeleportAsync(player, teleportData, useSameServer, requireConfirmedExit=true)`:
  - `TeleportOptions:SetTeleportData({ sessionRestore = { placeId, jobId, cframe, afkRejoin=true, preferSameServer, syncRestore } })`
  - `sameServer` → `options.ServerInstanceId = game.JobId`
  - **`requireConfirmedExit=true`** → hanya sukses kalau player benar-benar leave (bukan "no error within window")
  - Watch `TeleportInitFailed` event async
  - Timeout: `TELEPORT_INIT_TIMEOUT_SEC=10` / `TELEPORT_CONFIRM_TIMEOUT_SEC=15`
- **Sync restore:** panggil `syncService:captureSyncSnapshotForTeleport(player)` → validate via `AfkGuardDomain.validateSyncRestorePayload` → simpan di `pendingAfkSyncRestore[userId]`
- **Position restore setelah rejoin:** `pendingJoinRestore` / `pendingRespawnRestore` → `restoreAfterCharacterAdded` → `CharacterReady.waitForPositionRestore` + `pivotTo` + re-assert 2x untuk handle engine spawn drift
- **Ladder sameServer logic:** rung 1-2 (780s, 870s) → same server; rung 3-4 (960s, 1050s) → any public server
- **Fallback server warning:** kalau `afkRejoin && jobId != game.JobId` → notify `MSG_FALLBACK_SERVER`

### Rejoin detection (`RejoinMode`)
- `readAfkRejoinFlag()`: scan `teleportData.sessionRestore.afkRejoin == true` dari `player:GetJoinData().TeleportData` ATAU `TeleportService:GetLocalPlayerTeleportData()`
- Cached sekali; `RejoinMode.isAfkRejoin()` dipakai LoadingBootstrap (skip loading), JoinCommunityPromptController (skip prompt), Main.client (instant dance/music restore)

## 5. Investigasi: Bocor ke Kick 20:00 (intermittent)

### Konteks masalah (dari user)
- AFK rejoin thebasic **intermittent bocor** — player kena idle-kick Roblox 20:00 padahal seharusnya ladder menyelamatkan
- Pola: intermittent / susah reproduce (terjadi kadang-kadang, tidak merata di semua device)
- User belum cek log server (`afk_cycle_lost_player` / `afk_teleport_failed` / `denied_*`)
- User curiga `Player.Idled` kurang reliable

### Findings explore agent (verified 2026-08-25, instance:w41-9hp)
- **ClubKitConfig TIDAK override AfkGuard** — pakai kit defaults. Bukan masalah config.
- **`Config.FeatureFlags.AfkGuardEnabled` TIDAK ADA** di defaults + ConfigBootstrap tidak map entry AfkGuard. Controller check `== false` cuma work by accident (nil==false=false). Unmaintainable tapi coincidentally ON.
- **inifix TIDAK punya AfkGuard system** — hanya client module `Client.Modules.AFK` (sederhana, tanpa server guard). **Tidak ada yang worth di-port sebagai mitigation.** Thebasic justru lebih sophisticated, perlu di-FIX bukan di-ganti.

### Root cause (ranked by likelihood, verified via source code)

#### H2+H3 = Penyebab paling probable "intermittent bocor" ★★★★★
**Dua bug saling memperkuat:**
1. **`TELEPORT_CONFIRM_TIMEOUT_SEC=15s` terlalu pendek** — teleport cross-server Roblox routinely 10-30s under load. Timeout 15s → `safeTeleportAsync` return `(false, "teleport_unconfirmed")` → `handleAfkRejoin` return `Result.Err` → server respond `rejoin_failed`.
2. **`rejoin_failed` adalah outcome NON-transient** — `AfkGuardDomain.isTransientDenial()` hanya cover `denied_rate_limited | denied_in_flight | denied_carry_active`. `rejoin_failed` TIDAK di-cover → `isTransientDenial` return false → rung TETAP `firedSteps[stepIndex]=true` permanently → ladder kehilangan 1 rung selamanya.
3. **Efek domino**: teleport flaky → rung 3 (960s) latch permanent → rung 4 (1050s) juga latch → hanya butuh 2 flaky teleport → ladder mati sebelum 20:00 → player kena kick **diam-diam** (tidak ada log karena `resolveLadderStep` return nil, client tidak fire apa-apa).

**Cocok dengan gejala "random, susah pinpoint"** — teleport flakiness intermittent, ladder silent dead.

#### H1 — Boundary kritis rung 4 → hard stop ★★★★
- Rung 4 `atIdleSec=1050`, hard stop `19*60=1140`. Hanya 90s gap.
- Player.Idled fire tiap 30s (per comment controller) → hanya 3 retry tick (1050, 1080, 1110, 1140).
- Tick 1170 → `1170 > 1140` (strict `>`) → `resolveLadderStep` return nil → **LADDER DEAD**.
- Kalau semua 3 tick transient deny (e.g. carry-active partner), player burn semua headroom → kick.
- Any player yang lagi di-carry → `denied_carry_active` di setiap rung 4 tick → burn semua 3 headroom → kick.
- Tidak ada rung 5, tidak ada fallback.

#### H4 — Player.Idled reliability unverified ★★
- Comment controller: "Measured 2026-08-25, empirical, EXACTLY every 30s" — **single same-day measurement**, belum verify across devices.
- Kalau Idled skip tick di mobile/background tab, rung 4 window 90s bisa miss.
- `prevIdleSec` regression check **hanya deteksi drop**, bukan **stall** (stall monotonic, tidak terdeteksi).
- **Tidak ada heartbeat fallback** — ladder 100% gated pada Idled firing.

#### Race condition (low risk, documented for completeness) ★
`resetIdleState` swap `cycle` ke table baru. Pending response handler pegang OLD reference → write ke garbage (harmless). Inverse: response baru sampai setelah `resetIdleState` → new cycle `firedSteps` tetap → rung skip di new streak. Low impact karena fresh streak start dari 0s, baru threshold ~13min.

### Math boundary analysis (1050→1140)
| idleSec | event | rung 4 state |
|---------|-------|-------------|
| 1050 | fire rung 4 | fired |
| 1050+t | transient deny → un-fire | cleared |
| 1080 | re-fire rung 4 | fired |
| 1080+t | transient deny → un-fire | cleared |
| 1110 | re-fire rung 4 | fired |
| 1110+t | transient deny → un-fire | cleared |
| 1140 | `idleSec > 1140`? **No** (strict `>`) → fire rung 4 | fired |
| 1170 | `1170 > 1140` → `resolveLadderStep` returns **nil** | **LADDER DEAD** |
| 1200 | Roblox idle-kick | 💀 |

**Headroom: exactly 3 transient-denial ticks (90s). A 4th denial at 1140 still fires (good), but a denial at 1170 is fatal.** No rung 5, no fallback.

## 6. Design Fix Enterprise-Grade (production, root-cause)

**User intent:** Bukan catch-the-tail patch (tambah rung / bump timeout sebagai band-aid). Mau root-cause fix yang production/enterprise grade — robust, observable, fail-safe.

**KESIMPULAN: JANGAN port dari inifix.** inifix client-only tanpa server guard justru lebih lemah. Thebasic perlu di-FIX secara holistik.

### Koreksi root cause (dari verifikasi design agent)
- **H4 (feature flag phantom) FAKTUAL SALAH** — `AfkGuardEnabled = true` ADA di Config:1537. Gating `~= false` di Main.client:1446 / Main.server:1327 intentional permissive (null coalesce to true). ConfigBootstrap feature map (715-741) memang omit `AfkGuard` alias — **minor plumbing gap, bukan root cause bocor**.
- **H5 (new, latent contradiction)**: `AfkGuardDomain.luau:38-39` comment bilang "transient denials must not burn attempt budget", tapi `isTransientDenial` (line 100-104) justru EXCLUDE `denied_service_unavailable` & `rejoin_failed`. Ini **real root permanent-latch bug** — domain layer kontradiktif dengan comment-nya sendiri.
- **H6 (new)**: `inFlightStaleAfterSec` (35s) harus track confirm window. Kalau confirm naik ke 30s, stale harus 50s+. Kalau tidak, late-landing teleport collide dengan re-fired request = **double-teleport risk**.
- **H7 (new)**: `resolveLadderStep` return nil past `HARD_STOP_IDLE_SEC` = **silent client-side dead-end**, zero telemetry. Player ride clock ke 20:00 kick tanpa client log. Hanya server `afk_cycle_lost_player` fire.

### A. Transient vs permanent denial — outcome taxonomy redesign
**Root cause: H5, H2, H3.** Split outcomes jadi 3 tier (bukan 2). Client un-fire decision driven by tier, bukan hand-maintained allowlist.

| Tier | Outcomes | Client action |
|------|----------|---------------|
| Success | `allowed` | keep fired, cycle continues |
| Transient (retry-able) | `denied_rate_limited`, `denied_in_flight`, `denied_carry_active`, `denied_service_unavailable`, `rejoin_failed` | un-fire rung, re-arm with cooldown+jitter (Section C) |
| Permanent (genuine client fault) | `denied_invalid` | keep fired, escalate next rung; log loudly |

Distinguish teleport-flaky vs genuine failure: server return `rejoin_failed` carrying **reason string**. Reason ∈ `{teleport_unconfirmed, teleport_init_failed, teleport_async_thrown}` = transient (infra). Reason ∈ `{no_restore_cframe, character_missing}` = permanent-ish tapi still recoverable next rung. TeleportAsync failures always retry-able at API level — domain never sees "genuine permanent teleport failure".

**Code change** — `AfkGuardDomain.luau`:
```lua
function AfkGuardDomain.outcomeTier(outcome: RejoinOutcome): "success" | "transient" | "permanent"
    if outcome == "allowed" then return "success" end
    if outcome == "denied_invalid" then return "permanent" end
    return "transient"  -- rate_limited, in_flight, carry_active, service_unavailable, rejoin_failed
end
function AfkGuardDomain.isTransientDenial(outcome) return outcomeTier(outcome) == "transient" end
```
Wire `AfkGuardController.luau:120-122` response handler ke `outcomeTier`. Add `reason` field ke `RejoinResponse` (domain type line 49-53).

**Edge cases**: (1) permanent `denied_invalid` NOT retry — keep fired, ladder escalate. (2) Server `rejoin_failed` no reason → default transient (fail-open — better retry than dead-end genuine AFK player).

### B. Teleport confirmation & timeout — adaptive window + anti-double-teleport
**Root cause: H3, H6.** Keep `requireConfirmedExit=true` (correct — "no error within window" reported no-op teleport as success before). Replace single 15s window:
- `TELEPORT_CONFIRM_TIMEOUT_SEC_SAME_SERVER = 30` (cross-server-to-same-JobId still via Roblox matchmaking)
- `TELEPORT_CONFIRM_TIMEOUT_SEC_ANY_SERVER = 20` (any-server faster)
- `TeleportInitFailed` race parallel (already present `SessionCommandService.luau:54-65`)

Client pass `sameServer` in request → `AfkGuardService` pass through → `handleAfkRejoin` select window.

**Anti-double-teleport** (real new risk after Section A un-fires `rejoin_failed`): server-authoritative `inFlightAfkRejoin` guard (`AfkGuardService.luau:214`) = single authority. While set, ANY new request for same userId → `denied_in_flight` (transient). Stale-reaper `inFlightStaleAfterSec` MUST = `confirm_window + slack`. Confirm=30s → stale=50s. Comment `SessionCommandService.luau:124-129` ("if teleport lands late, player gone") only true BECAUSE rungs latch permanently; after Section A, in-flight guard becomes **load-bearing**.

**Code changes**:
- `Config.luau`: replace `TELEPORT_CONFIRM_TIMEOUT_SEC=15` dengan 2 keyed variants
- `SessionCommandService.luau:84-87` `safeTeleportAsync`: pick window by `sameServer`
- `AfkGuardService.luau:21-26` `inFlightStaleAfterSec`: `max(confirmSame, confirmAny) + 20`

**Edge cases**: (1) TeleportInitFailed fire at 5s → return `(false, "teleport_init_failed")` immediately. (2) `player.Parent==nil` at poll → success. (3) Window expire no signal → `teleport_unconfirmed` → transient, rung re-arm. (4) Third request while two in-flight → denied `denied_in_flight`, no teleport storm.

### C. Ladder re-arm strategy — per-rung cooldown with jitter, never permanent
**Root cause: H2, H1.** `firedSteps[index]` change from boolean ke **timestamp when rung may re-fire** (`nil` = ready). On transient denial, re-arm time = `now + retryAfterSec` (server-supplied) + ±10% jitter (reuse `nextRetryDelaySec` `AfkGuardDomain.luau:108-118`). On permanent denial, re-arm = `math.huge` (never), tapi ladder escalate next rung same tick.

`resolveLadderStep` (`AfkGuardDomain.luau:174-194`) gain `now: number` param, treat `firedSteps[index]` as deadline:
```lua
for index, step in ipairs(ladder) do
    local armedAt = firedSteps[index]
    local ready = armedAt == nil or now >= armedAt
    if idleSec >= step.atIdleSec and ready then chosenIndex = index end
end
```
"Highest not-yet-fired" semantic preserved; re-armed rung re-fire on next eligible tick. Tight retry loop prevented by cooldown floor (min 30s) + jitter. If all transient rungs on cooldown simultaneously + idle past last rung → Section E panic mode.

**Permanent-denial rungs**: `denied_invalid` set `firedSteps[index] = math.huge`. Only fires on payload validation failure = client bug — buggy client should escalate, not silently retry.

**Edge cases**: (1) idle regression reset `firedSteps` entirely (`resetIdleState`) — unchanged. (2) Client clock skew vs server `retryAfterSec` — use `os.clock()` deltas, not wall time. (3) All rungs permanent → Section F.

### D. Dead-man heartbeat untuk Player.Idled reliability
**Root cause: H1 "3 Idled ticks @30s" assumption + H4 Idled unreliability.** `Player.Idled` = primary signal. Deadman heartbeat = `RunService.Heartbeat` loop estimate idleSec dari `UserInputService:GetLastInputTime()` (engine-authoritative, monotonic, all platforms) when Idled not fire >35s past expected tick. Deadman switch: only run when Idled stalls, defer to Idled whenever fire (no duplicate detection).

```lua
-- Client, Heartbeat loop, every 5s
local lastInputT = UserInputService:GetLastInputTime()  -- seconds since epoch
local estimatedIdle = workspace:GetServerTimeNow() - lastInputT  -- if Idled stalled
if estimatedIdle >= expectedNextRungSec and not idledFiredRecently then
    -- fire ladder as if Idled had fired with estimatedIdle
end
```
`GetLastInputTime` = seconds since epoch (not os.clock) → convert via `workspace:GetServerTimeNow()` for cross-platform accuracy.

**No double-fire**: set `idledFiredRecently = true` for 31s after every Idled tick; heartbeat skip while set. If Idled resume, set flag; heartbeat never race.

**Edge cases**: (1) `GetLastInputTime` return 0 before first input — heartbeat skip until first real input. (2) Server time not synced at join — fall back to `os.clock()` delta from captured join timestamp. (3) Heartbeat fires same rung Idled would have — rung fired-set prevent double-fire (Section C). (4) Mobile background-throttling — heartbeat also throttles, but on resume catch up in one tick (estimatedIdle jumps).

**Log**: `afk_idle_stall_detected` `{ stalledForSec, estimatedIdleSec, lastIdledIdleSec }` — new observability signal (Section F).

### E. Hard stop & ladder boundary — panic mode past 19min
**Root cause: H1, H7.** Do NOT widen 90s gap by add rung 5 (band-aid). Instead: past `HARD_STOP_IDLE_SEC` (1140s), enter **panic mode** — ladder does NOT return nil. Fire best-effort re-arm of last any-server rung every 30s with fresh cycle, karena attempting teleport + risking mid-disconnect landing strictly better dari guaranteed 20:00 kick.

```lua
-- resolveLadderStep, after chosenIndex loop
if chosenIndex == nil and idleSec > AfkGuardDomain.getHardStopIdleSec() then
    local lastAny = #ladder  -- assume last rung is any-server
    local armedAt = firedSteps[lastAny]
    if armedAt == nil or now >= armedAt then
        return lastAny, ladder[lastAny]
    end
end
return chosenIndex, ladder[chosenIndex]
```
Fail-safe: panic teleport land mid-disconnect = clean reconnect on new server, better dari certain kick. "Teleporting into kick window is worse than letting disconnect happen cleanly" is NOT true once alternative = guaranteed kick — panic rejoin can only help.

**Edge cases**: (1) Panic rung on cooldown — skip tick, try next Heartbeat tick. (2) Rate limiter deny panic cycle — `denied_rate_limited` transient, re-arm. (3) Player move at 18:59 — idle regression reset, no panic.

### F. Silent failure observability — client-side telemetry
**Root cause: H7.** Client currently log `afk_rejoin_requested`, `afk_rejoin_result`, `afk_cycle_reset_by_input`. NOT log: (a) ladder exhaustion, (b) all rungs permanent, (c) Idled stall, (d) panic mode, (e) repeated transient denials same rung.

Add to `AfkGuardController.luau`:
- `afk_ladder_exhausted` — `resolveLadderStep` return nil + idleSec < HARD_STOP + all rungs fired (not cooldown). Warn.
- `afk_ladder_all_permanent` — all rungs `firedSteps[i] == math.huge`. Error. Smoking-gun client bug.
- `afk_idle_stall_detected` — from Section D. Info (first) then warn (repeats).
- `afk_panic_mode_activated` — from Section E. Warn.
- `afk_rung_transient_replay` — rung re-fire after transient denial, `{ stepIndex, attemptCountWithinCycle }`. Spot rung that keeps denied.

Server `AfkGuardService.luau` already has `afk_cycle_lost_player`. Add:
- `afk_cycle_ladder_dead_client_reported` — client fire telemetry remote (new `AfkGuardTelemetry`) report ladder-dead → server correlate with `activeCycles` state → log combined record. Closes gap client-side silent failure never reach server logs.

**Edge cases**: Telemetry remote fire-and-forget, rate-limited 1/30s, never blocks safety path (mirror `notifySafe` pcall pattern).

### G. Feature flag plumbing — component-level granularity
**Root cause: minor ConfigBootstrap map gap (NOT phantom-flag H4).** Add `AfkGuard` to ConfigBootstrap feature map so `Features.AfkGuard = false` works via standard plumbing. Plus component-level sub-flags:

```lua
Config.FeatureFlags.AfkGuardSubcomponents = {
    ClientDetection = true,    -- Player.Idled + heartbeat (Section D)
    ServerGuard = true,         -- AfkGuardService admission
    Teleport = true,            -- handleAfkRejoin path
    SyncRestore = true,         -- dance sync restore on rejoin
}
```
`AfkGuardController.init` check `ClientDetection`. `AfkGuardService.handleRequest` check `ServerGuard`. `SessionCommandService.handleAfkRejoin` check `Teleport`. `SyncService.restoreAfterAfkRejoin` check `SyncRestore`. Operator can disable just teleport path (e.g. Roblox teleport outage) without losing client AFK warning.

**Edge cases**: (1) `Teleport=false` → `handleAfkRejoin` return `Result.Err("teleport_disabled")` → client `rejoin_failed` → transient → re-arm → player still get AFK warning. Fail-safe. (2) `ServerGuard=false` → remote still receive but `handleRequest` no-op; client rungs all re-arm. No silent kick.

### Risk & mitigation summary
| Risk | Mitigation |
|------|------------|
| Double-teleport after Section A un-fire rejoin_failed | Server-authoritative `inFlightAfkRejoin` guard 50s stale window (Section B/H6); client re-arm tapi server deny while in-flight |
| Heartbeat double-fires Idled | `idledFiredRecently` 31s skip flag; rung fired-set dedup (Section C) |

| Component flag misconfig leave player unprotected | Sub-flags default `true`; disable any still leave AFK warning + idle regression reset intact |

## 11. Performa & Efisiensi Analysis

User concern: design harus tetap efficient — performa, recv, dll. Berikut analisis tiap section dari lensa performa.

### Hot path analysis (apa yang fire sering)
- **`Player.Idled`**: fire tiap 30s saat idle. BUKAN hot path — hanya saat AFK. Saat active play, tidak fire.
- **`UserInputService.InputChanged`**: fire SETIAP FRAME saat mouse move. INI HOT PATH. `resetIdleState` saat ini sudah idempotent + allocation-free (cek `cycle.cycleId == nil && prevIdleSec == nil && next(firedSteps) == nil` → early return). Design baru tidak boleh break ini.
- **`RunService.Heartbeat`** (Section D): fire tiap frame (~60Hz). INI HOT PATH kalau tidak di-throttle. **WAJIB throttle** ke poll interval (e.g. 5s via accumulator), bukan cek tiap frame.
- **`requestRemote:FireServer`**: tidak sering (max 4 rung per cycle, tiap 30s saat AFK). Aman.
- **`responseRemote.OnClientEvent`**: tidak sering (1 response per request). Aman.

### Section-by-section performa

| Section | Performa concern | Mitigation |
|---------|------------------|------------|
| **A. outcomeTier** | Pure function, dipanggil di response handler (1x per response). Cost: O(1) string compare. | Aman. Lebih murah dari table lookup sebelumnya. |
| **B. Adaptive timeout** | `safeTeleportAsync` already poll `task.wait(0.25)` tiap 250ms. Extend 15→30s = poll count 60→120. Cost: 60 extra `task.wait` yield (cheap, no allocation). | Aman. `task.wait` yield tidak allocate. Server-side in-flight guard 50s stale = TTLSet reap (already periodic). |
| **C. firedSteps→deadline** | `resolveLadderStep` iterate ladder (4-5 rung, O(n) kecil). Dipanggil di `Player.Idled` handler (tiap 30s saat AFK). BUKAN hot path. | Aman. Table access + compare, no allocation. |
| **D. Heartbeat** | **POTENSI HOT PATH** kalau cek tiap frame. | **THROTTLE**: accumulator pattern, poll tiap 5s (`accum += dt; if accum >= 5 then`). `GetLastInputTime()` = O(1) engine call. `idledFiredRecently` flag = boolean check. Total cost per 5s: 2 function call + 1 compare. Negligible. |
| **E. Panic mode** | Branch di `resolveLadderStep` (already dipanggil tiap 30s saat AFK). Cost: 1 extra `#ladder` + 1 table access. | Aman. |
| **F. Telemetry** | `Logger:info/warn` = pcall + string format. Fire-and-forget remote = 1 FireServer per event. | **Rate-limit 1/30s** untuk telemetry remote. Logger sudah pcall-wrapped. Tidak di hot path. |
| **G. Feature flag** | `Config.FeatureFlags` table lookup at init. Once. | Aman. |

### Recv/network analysis
- **Request remote (C→S)**: 4-5 rung per cycle, tiap 30s saat AFK. Payload kecil (`{requestId, reportedIdleSec, cycleId, stepIndex}` ~100 bytes). Tidak ada peningkatan volume dari design baru — justru **turun** karena transient denial un-fire lebih efisien dari permanent latch (tidak ada retry storm).
- **Response remote (S→C)**: 1 per request, kecil (`{requestId, outcome, retryAfterSec, stepIndex}` ~80 bytes). Aman.
- **Telemetry remote (C→S, new)**: fire-and-forget, rate-limited 1/30s. Payload kecil (`{event, data}` ~50-100 bytes). Worst case: 2 event per 30s = ~200 bytes. Negligible.
- **In-flight guard server-side**: `inFlightAfkRejoin[userId]` = table entry, set/clear O(1). Stale reap periodic (already in `handleRequest`). 50s window vs 35s = 15s extra hold per entry, tapi hanya untuk player yang lagi AFK rejoin (rare).

### CPU/allocation analysis
- **Section C (firedSteps→deadline)**: `firedSteps[index]` dari boolean ke number. Tidak ada extra allocation — table entry tetap 1 slot. `resetIdleState` tetap swap table (sudah ada), tapi sekarang `firedSteps` berisi number bukan boolean — same memory.
- **Section D (Heartbeat)**: 1 accumulator variable + 1 boolean flag. No per-frame allocation. `GetLastInputTime()` return number (no GC).
- **Section A (outcomeTier)**: pure function, return string literal (no allocation — string interned).
- **No new tables per tick**: design tidak create table di hot path. `cycle` state tetap 1 table per streak (swap on reset, already existing pattern).

### Memory analysis
- `activeCycles[userId]` (server): 1 entry per AFK player, cleared on leave. TTL 600s. Tidak boros.
- `inFlightAfkRejoin[userId]` (server): 1 entry per in-flight teleport, cleared on confirm/leave/stale. 50s window vs 35s = sedikit longer hold, tapi rare (hanya saat teleport in-flight).
- `teleportWatchers[userId]` (server): 1 entry per attempt, cleared on done/leave. 30s window vs 15s = sedikit longer, tapi rare.
- Client `cycle` state: 1 table per streak. No growth.

### Verdict performa
**Design ini EFFICIENT.** Key reasons:
1. Semua hot path (`InputChanged`, `Heartbeat`) di-throttle atau early-return. No per-frame allocation.
2. Network volume TURUN (transient un-fire lebih efisien dari permanent latch retry storm).
3. Server-side state entry count tetap O(active AFK players) — rare, short-lived.
4. `outcomeTier` pure function O(1). `resolveLadderStep` O(n) dengan n=4-5.
5. Telemetry rate-limited, fire-and-forget, tidak di safety path.

**Yang perlu pastikan saat implementasi:**
- Heartbeat (Section D) WAJIB throttle ke 5s poll, bukan cek tiap frame. Pakai accumulator `accum += dt`.
- `GetLastInputTime()` return 0 sebelum first input — skip heartbeat sampai non-zero.
- Telemetry remote rate-limit 1/30s (mirror `notifySafe` pcall pattern).
- `resetIdleState` tetap idempotent + early-return saat state sudah clean (jangan break existing optimization).
