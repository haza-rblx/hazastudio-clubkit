# Performance hardening plan — 200 CCU / low-end mobile

## Goal

Improve existing Roblox systems without an architecture rewrite, preserving buyer-facing behavior and cleanup patterns. Changes remain backward-compatible and are applied only after approval.

## Phase 0 — Baseline and instrumentation

- Capture server/client Script Profiler and MicroProfiler baselines for idle, UI open/close, donation burst, overhead effects, gravity transitions, respawn, and 8-client playtest.
- Add or verify counters for active Heartbeat/RenderStepped connections, NetworkManager flush mode, remote requests/events per endpoint, payload bytes, DataStore queue depth, deferred/retry/rejected requests, and active donation effects.
- Verify effective runtime configuration for shared network flushing, proximity incremental mode, quality settings, streaming settings, and DataStore save intervals.
- No behavior change in this phase; use measurements to set before/after thresholds.

## Phase 1 — Safe CPU and cleanup fixes

1. Title/overhead animation scheduler: route animated TitleColorPreset effects through the existing SharedTick scheduler; guarantee idempotent start/stop and cleanup on title change, character removal, respawn, and PlayerRemoving; preserve visual timing.
2. Gravity physics lifecycle: ensure at most one active physics Heartbeat/LinearVelocity state per player and mode; make transitions idempotent; preserve the current command API.
3. Network flush configuration: keep shared flush enabled in production; prevent accidental per-instance Heartbeat fallback except an explicitly documented development rollback; add telemetry.
4. Feature-scoped frame loops: audit Drone, Freecam, Hotbar/Inventory drag, AvatarViewport, Loading/Cinematic, BoardAmbience, and Overhead UI; start only while active/visible and stop on close, cancel, destroy, respawn, and player removal.

## Phase 2 — Client/UI and effects

1. DonationNotificationController: bounded cache for TextService text measurements; prevent duplicate marquee workers; stop work while hidden; bound notification queue and effect concurrency; coalesce redundant updates.
2. UI cost controls: measure active versus hidden GuiObjects before changing hierarchy; virtualize or pool long ScrollingFrame lists only where confirmed necessary; gate expensive UI animation by visibility and quality tier.
3. Low-end quality tier: scale particles, animated gradients/strokes, blur/camera shake, viewport animation, and donation effects while preserving touch targets and safe-area behavior.
4. Audio/effect memory: avoid preloading the full donation/effect library on low-end devices; pool or destroy one-shot instances; cap concurrent effects; use distance/recipient culling.

## Phase 3 — Network and persistence scaling

- Inventory every FireAllClients, FireClient, OnServerEvent, and InvokeServer endpoint with authorization, type/payload bounds, rate limit, frequency, and recipient scope.
- Replace broad broadcasts only where runtime evidence shows unnecessary fan-out; use nearby recipients, relevant subscribers, revisioned state, and batching.
- Audit DataStore repositories through DataStoreScheduler; coalesce dirty writes; protect join/leave bursts; separate critical profile saves from cosmetic writes.
- Validate retry/backoff and shutdown/PlayerRemoving behavior without changing DataStore keys or migration semantics.

## Verification

- Run focused Luau tests for pure scheduler, rate-limit, batching, and cache logic where seams exist.
- Run Studio device simulation for low-end mobile, tablet, and console-like viewports.
- Repeat MicroProfiler/F9 captures and compare p50/p95/p99 frame time, script time, memory categories, active connections, network KB/s/events/s, and DataStore queue metrics.
- Run 8-client multiplayer tests, then staged bot/load simulation for 50, 100, 150, and 200 logical players.
- Hold a 2-hour soak test and require memory plateau, no connection/instance growth after repeated UI open/close and respawn, no sustained server FPS below 55, and low-end client FPS at or above 30 in normal gameplay.

## Guardrails

- Do not rewrite architecture or change public remotes/DataStore keys unless profiling proves a Critical bottleneck and the change is separately approved.
- Do not modify buyer-owned config/secrets automatically.
- Do not commit or modify implementation files until the user approves this plan.
