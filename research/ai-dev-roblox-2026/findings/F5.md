# F5: Agent workflow patterns that practitioners report actually work for solo developers / small teams in 2025-2026 (spec-driven development, persistent memory/context management, verification loops, guardrails, and anti-patterns)

## Findings

### [1] Anthropic's official Claude Code best-practices guide (2026 edition) makes "give the agent a runnable check before it can claim done" the #1 pattern — without a verification signal, the human becomes the verification loop
- quote: "Give Claude a check it can run: tests, a build, a screenshot to compare. It's the difference between a session you watch and one you walk away from... Without a check it can run, 'looks done' is the only signal available, and you become the verification loop"
- url: https://www.anthropic.com/engineering/claude-code-best-practices
- source_type: primary
- published: unknown (fetched 2026-10-01; current 2026 edition)
- confidence: high

### [2] Anthropic documents a graduated guardrail ladder for verification: in-prompt check → `/goal` condition re-checked each turn → deterministic Stop hook that blocks turn end until the check passes → independent verification subagent that tries to refute the result
- quote: "As a deterministic gate: a Stop hook runs your check as a script and blocks the turn from ending until it passes... a verification subagent or a dynamic workflow that checks its own findings has a fresh model try to refute the result, so the agent doing the work isn't the one grading it"
- url: https://www.anthropic.com/engineering/claude-code-best-practices
- source_type: primary
- published: unknown (fetched 2026-10-01)
- confidence: high

### [3] Anthropic's CLAUDE.md guidance: keep it short and pruned — bloated instruction files cause agents to ignore the actual rules; only include what the agent cannot infer from code; convert reliably-followed rules into deterministic hooks instead
- quote: "Keep it concise. For each line, ask: 'Would removing this cause Claude to make mistakes?' If not, cut it. Bloated CLAUDE.md files cause Claude to ignore your actual instructions!... If your CLAUDE.md is too long, Claude ignores half of it because important rules get lost in the noise. Fix: Ruthlessly prune. If Claude already does something correctly without the instruction, delete it or convert it to a hook."
- url: https://www.anthropic.com/engineering/claude-code-best-practices
- source_type: primary
- published: unknown (fetched 2026-10-01)
- confidence: high

### [4] Anthropic's context-management guidance: `/clear` between unrelated tasks beats long sessions; after two failed corrections on the same issue, wipe context and restart with a better prompt — "a clean session with a better prompt almost always outperforms a long session with accumulated corrections"
- quote: "If you've corrected Claude more than twice on the same issue in one session, the context is cluttered with failed approaches. Run /clear and start fresh with a more specific prompt that incorporates what you learned."
- url: https://www.anthropic.com/engineering/claude-code-best-practices
- source_type: primary
- published: unknown (fetched 2026-10-01)
- confidence: high

### [5] Jesse Vincent's (obra) two-session architect/implementer workflow (Oct 2025): brainstorm into a design doc in docs/plans/, generate a bite-sized implementation plan, then have a separate fresh-context implementer session execute 3-4 tasks at a time while the architect session reviews each chunk — and `/clear` the implementer between chunks instead of `/compact`
- quote: "Next up, I open a *new tab* or window... fire up another copy of claude... 'Please execute the first 3-4 tasks... DO NOT DEVIATE FROM THE PLAN.'... When it's done, I'll flip back to the 'architect' session and tell it 'The implementer says it's done tasks 1-3. Please check the work carefully.'... And then, I don't */compact*. Instead I */clear* the implementer and start the conversation over."
- url: https://blog.fsck.com/2025/10/05/how-im-using-coding-agents-in-september-2025/
- source_type: primary
- published: 2025-10-05
- confidence: high

### [6] Jesse Vincent's anti-credulity technique for automated review output: prefix pasted review feedback with a role-play prompt forcing the agent to evaluate the reviewer ("should we hire this reviewer") instead of blindly applying suggested fixes
- quote: "our robot buddies are quite credulous. If you paste in a list of instructions for how to update a codebase, Claude's just going to take you at your word and make the changes, even if what you're asking for is crazy and wrong... 1) should we hire this reviewer 2) which of the issues they've flagged should be fixed? 3) are the fixes they propose the correct ones?"
- url: https://blog.fsck.com/2025/10/05/how-im-using-coding-agents-in-september-2025/
- source_type: primary
- published: 2025-10-05
- confidence: high

### [7] Simon Willison (Oct 2025): parallel agents work best for low-stakes or self-specified work — research spikes, "how does X work" explanations (saved as reusable prompt context), warning/deprecation fixes, and work built from your own detailed spec, which is far cheaper to review than code arriving "out of nowhere"
- quote: "Code that started from your own specification is a lot less effort to review. If you already decided what to solve, picked the approach and worked out a detailed specification for the work itself, confirming it was built to your needs can take a lot less time."
- url: https://simonwillison.net/2025/Oct/5/parallel-coding-agents/
- source_type: primary
- published: 2025-10-05
- confidence: high

### [8] Simon Willison's guardrails posture: he runs local agents in YOLO mode only when confident no malicious instructions can enter context, prefers async cloud agents (Codex Cloud) for riskier tasks to limit blast radius, uses fresh checkouts into /tmp rather than git worktrees for isolation, and notes he "needs to start habitually running local agents in Docker containers"
- quote: "running in YOLO mode (no approvals) for tasks where I'm confident malicious instructions can't sneak into the context... For riskier tasks I'm currently using asynchronous coding agents—usually Codex Cloud—so if anything goes wrong the worst that can happen is my source code getting leaked"
- url: https://simonwillison.net/2025/Oct/5/parallel-coding-agents/
- source_type: primary
- published: 2025-10-05
- confidence: high

### [9] HN practitioners (Feb 2026 thread, "Are you still using spec driven development?") report GitHub Spec Kit remains reliable for brownfield work, but as prompting skill improves, straight prompting returns for simple changes — spec-driven is one tool, not a mandatory religion
- quote: "Personally, I still find tools like spec kit give reliably good results in brownfield codebases, but that as I've improved my ability to break apart work and describe it, straight prompting has come back as a viable method to perform simple changes."
- url: https://news.ycombinator.com/item?id=46864948
- source_type: community
- published: 2026-02-03
- confidence: medium

### [10] HN practitioner consensus on doc-file discipline for agents: maintain CLAUDE/AGENTS/README/ARCHITECTURE/planning docs, keep each file around ~750 lines (planning files max ~1,500 or split into phases), beware context drift from over-stuffing, use different models adversarially to check plans, and always test manually
- quote: "I find the sweet spot is ~750 lines for each file. Planning files can max out at 1,500 lines if needed or otherwise broken up into individual phases... I'd add caution about drift. The more documentation you shove into the context, the worse things can get... use different AI models adversarially... Usually ChatGPT can spot Claude's blind spots... And always test manually."
- url: https://news.ycombinator.com/item?id=46864948
- source_type: community
- published: 2026-02-05
- confidence: medium

### [11] A solo-consultant HN workflow that mirrors spec-driven development without tooling: feed contract/discovery transcripts/architecture diagrams into the LLM, generate epics/stories/phases as markdown checklists committed to the repo, have the agent update the doc with progress and guidance each session, and treat agents as junior devs with manual test-and-verify gates per phase
- quote: "Finally, I ask it to give me unrendered markdown with the details and a checklist and that's the starting point of my repo... I tell them to update my document with what's done, guidance I've given it etc. I treat both of them like junior devs and keep my hands on the wheel and test and verify each phase."
- url: https://news.ycombinator.com/item?id=46864948
- source_type: community
- published: 2026-02-04
- confidence: medium

### [12] Reported anti-pattern (HN, Dec 2025, 66-comment production-monorepo thread): agent.md-style rule files are not reliably followed across tools — one startup found Cursor respected .cursor/rules but "other tools struggle to consistently read or follow these rules no matter how many agent.md-style files we add"; their fallback was heavy pre-commit hooks (ty, ruff, TS checks, tests, formatting) as the deterministic enforcement layer
- quote: "We rely heavily on pre-commit hooks: ty, ruff, TypeScript checks, tests across all languages, formatting, and other guards... Cursor generally respects this, but other tools struggle to consistently read or follow these rules no matter how many agent.md-style files we add."
- url: https://news.ycombinator.com/item?id=46292682
- source_type: community
- published: 2025-12-16
- confidence: medium
