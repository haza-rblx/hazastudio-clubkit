# CONTEXT — Hazastudio Club Kit

Domain glossary for agents. Terms only — no implementation details, no workflow steps (those live in `AGENTS.md`). When a term here conflicts with how someone uses it, the glossary wins or gets updated in the same conversation.

## The product

- **Kit** — the Hazastudio Club Kit as a whole: the product buyers install into their Roblox place.
- **Engine** — the replaceable core of the Kit: the `Hazastudio_ClubKit` folders under ReplicatedFirst, ReplicatedStorage, ServerScriptService, StarterPlayerScripts, plus related StarterGui. Updated wholesale on release.
- **Showcase** — `ClubKitShowcase`, a dev-only demo assembly. Not part of the Engine; never shipped via source sync.

## Ownership boundary

- **Buyer-owned files** — `ClubKitConfig.luau` (ReplicatedStorage) and `Secrets.luau` (ServerScriptService). The buyer's data lives here; the Kit never overwrites them (see `docs/adr/0001`).
- **Fill-forward** — the additive merge that brings new config keys to an existing buyer config: missing keys are added from the schema, existing buyer values are preserved. Happens at runtime (`ConfigBootstrap`, in-memory) and after plugin engine updates (source patch from `ClubKitConfigSchema`).
- **Schema** — `ClubKitConfigSchema`: the canonical list of config keys, source of truth for fill-forward and for the template `ClubKitConfig.luau`.

## Release

- **Version triad** — the three places the kit version must agree: `VERSION` (repo root), `KitProduct.KitVersion` (engine), `ClubKitManifest.KIT_VERSION` (packager plugin).
- **Source sync** — the primary release channel: git tag on the public repo, fetched by the Studio plugin's Update Engine action. Engine-only; config is fill-forwarded, never replaced.
- **RBXM release** — the rare full-fidelity channel: a `.rbxm` export for fresh installs or non-engine assets (StarterGui, Workspace boards, ServerStorage).
- **Release folder** — `docs/releases/<X.Y.Z>/` holding `UPGRADE.md` (buyer guide) and `CHANGED_FILES.md` (grouped Replace / Buyer-owned / Optional).

## Code structure

- **Init bag** — a module under `Client/Init/*` or `Server/Init/*` that returns a table of related modules from one `require`, keeping top-level `local` counts low in Main scripts.
- **Register budget** — Luau's ~200 local-registers-per-chunk limit; the structural pressure behind Init bags (see `docs/adr/0002`). Frozen at ≥170 top-level locals in a file, blocker at ≥185.
- **Versioned DataStore keys** — player-data keys carry a version; bumping one is a breaking migration for existing buyers' live data.

## Persistence (production hardening, 2026-09-24)

- **Session document** — a player's Overhead (or Settings) document held in `PlayerSessionStore` while they are in the server; changes are written behind (debounced flush), not per change.
- **Stale session** — a session with unsaved changes that another server wrote over (cross-server invalidate, or a newer stored `_version`). It is kept, never dropped; its next flush **replays** the session's unsaved mutators onto the stored document inside `UpdateAsync`.
- **Departed session** — a leaver's document (or venue quest progress) whose final write has not succeeded yet. Kept and retried until written; a rejoin in the same server gets it back.
- **Budget refusal** — `budget_low` / `budget_exhausted` from the DataStore admission gate. ProfileLoader requeues any kind refused this way; after the last delay it reports `load_gave_up`.
- **BudgetMeter** — the per-server counter of DataStore / HTTP / MessagingService use and budget events; logged once a minute, shipped to the VPS from P3.

## UI motion

- **Rasterized group** — a `CanvasGroup`: Roblox flattens its subtree into a GPU texture sized by its `AbsoluteSize`. Resizing re-creates the texture; exceeding the client's texture budget renders it blank (Roblox docs).
- **Phantom UIComponent (P0b, 2026-09-17)** — a `UICorner`/`UIStroke` that exists only as a `StyleRule` (`.tag::UICorner`) applied through a `StyleLink`, not as a child instance. Renders pixel-identically to the real one and is not counted by `Stats.InstanceCount`, but code cannot find it with `FindFirstChild*`; read it with `GetStyled(prop, "::UICorner")`. A corner's design lives in its four per-corner radii — `CornerRadius` is a lossy shorthand. A real `UICorner` child overrides the phantom; a real `UIStroke` does not — both strokes render, stacked by `ZIndex`. Works identically under a `CanvasGroup`; a stroke's `UIGradient` child is phantomed with `.tag::UIStroke::UIGradient`.
- **Size-stable motion** — the rule that nothing may change a rasterized group's `AbsoluteSize` while it is visible (see `docs/adr/0005`). Scale pops on groups become fades/travel; plain Frame trees keep the pop.
- **Group motion policy** — `Shared/UI/GroupMotionPolicy` (pure) + `Client/Utils/GroupMotion` (Instance adapter): the single decision point for "scale or stable?" that every animation site consults via `GroupMotion.scaleTarget`. Opt-out knob: `Config.UIMotion.CANVAS_GROUP_SIZE_STABLE`.
- **Motion vocabulary (ADR 0011, 2026-09-14)** — `Client/Utils/UIMotion` is the one module for everything a panel does *between* open and close: press squash (`bindPress`), hover lift on pointer devices (`bindHover`), `pop`/`popIn`, `wiggle`/`spin`, `fadeIn` + `captureBases` + `stagger` for rows, `slideIn`/`slideInVertical` for tab pages (equal-and-opposite `UIPadding`, so a laid-out page never changes size), `pulse`, `countTo`, and a per-property-channel `tween`. It decides layout safety itself, in tiers (next bullets): the button scales only when it is a centred element whose parent has no layout and which is not in a `CanvasGroup`; otherwise its icon, then its one label, then padding/brightness. Runtime-only names it creates: `UIMotionScale`, `UIMotionSlide`, `UIMotionRotation`, `UIMotionIconSlot`; audit attributes `UIMotionBound` (which tier a button took), `UIMotionSlideRefused` (a slide that was refused, and on which axis) and `UIMotionOwned` (a `UIScale` UIMotion created). Grew out of the v3 music panel's `MusicMotion`, which no longer exists.
- **Press fallback (ADR 0011 addendum, 2026-09-15)** — what `bindPress`/`bindHover` do on a button where `scaleTargetOf`, `iconTargetOf` and `textTargetOf` all return nil (the button lays its own children out, has no children or icon or lone label, or sits under a `CanvasGroup`), so a bind is never silent: press insets the button's *own* `UIPadding` 2–6 px on all four sides (`clamp(shorter side × 0.06, 2, 6)`, through the same one-per-instance/designed-values-as-attributes mechanism `slideIn` uses) and springs back Back-Out — internal, so the button's `AbsoluteSize` and its siblings never move and it is legal under a rasterized group; a childless or `AutomaticSize` button gets a brightness dip instead (`BackgroundColor3` 15% toward black, else `ImageColor3`, else `TextTransparency` +0.25), and hover always uses brightness only (8% toward white). Audit attribute `UIMotionBound`, strongest wins: `true` (button scale) > `"icon"` > `"text"` > `"fallback"` (padding/brightness) > `"no-target"` (nothing painted at all); `UIMotion.markBound` is its one writer (`PressFeedback` calls it).
- **Icon tier (ADR 0011 addendum, 2026-09-16)** — the tier below button scale (the text tier and the padding/brightness fallback sit under it), and the owner's answer to "hover should not wash the button white": when `scaleTargetOf` refuses the button but the button paints an icon (`UIMotion.iconTargetOf` — a visible `ImageLabel`, or an *inactive* `ImageButton`, as a direct child or one level inside any visible non-button container; an active nested `GuiButton` is never taken, it has its own bind), hover lifts that icon to **1.08×** its rest and press squashes it to **0.92×**, through the same borrowed-`UIScale`/captured-rest machinery as the button tier. **Icon chip** — the shape most kit icons actually have, and the reason the tier reaches them: a styled badge (`UICorner` + `UIGradient` + `UIAspectRatioConstraint`) whose *own* `Image` is empty because the art sits in an `ImageLabel` nested inside it (all nine top bar rows, the music playlist covers, the cinematic dock rows — 63 buttons). The chip counts as the icon when it holds image-bearing art **and no visible non-empty text of its own**, and the chip is what scales, so corner, gradient and art grow together and a row whose chip carries a leftover placeholder image behaves identically to one whose chip is empty. The no-text clause is the guard against a button's full-bleed *background* image, which holds the row's words and would drag the whole row's content up with it; it is a shape test, not a size test, which is why a 99×99 playlist cover filling its card's face still qualifies (its title and artist sit outside it). A chip rejected for holding text is not lost — the wrapper scan then reaches the art inside it and lifts that instead. The icon is scaled **in place** only when nothing can reflow (its parent has no `UIGridStyleLayout`, and neither its parent nor the button has `AutomaticSize ~= None`); otherwise it is moved once into a **`UIMotionIconSlot`** — a `Frame` that takes the icon's own `Size` property together with its `Position`/`AnchorPoint`/`LayoutOrder`/`ZIndex`/`SizeConstraint` and its `UIAspectRatioConstraint`, which keeps the layout footprint while the icon — now `fromScale(1, 1)` and centred inside it — scales and overflows (measured: a bare `UIScale` on the top bar `ShopButton`'s 38×38 icon grew the row to 41 px and shoved its sibling +3 px). **The slot copies `Size`; it never measures `AbsoluteSize` (corrected 2026-09-16).** An earlier build pinned it to a measured rest `AbsoluteSize` in offsets, which broke twice over: the measurement had to be taken at bind time, and pooled rows are bound before their first layout pass (`AdminPanelV3UI` binds a player card while it is still a detached clone; `ListPool` parents rows `Visible = false` before `createRow`), so a pre-layout size was frozen forever — the music library's playlist covers rendered at 7.6 px inside a 106 px row and the Admin v3 `PlayerProfilePicture` at 14.1 px, 14 slots kit-wide under 35% of their button; and an offset is the wrong kind of value for a scale-sized icon anyway (`PlaylistCover` is `{0.5, 0}, {1, 0}`, `PlayerProfilePicture` is `{1, 0}, {1, 0}`), which stops tracking its row on any resize or phone scale. Copying `Size` needs no timing at all, because the slot stands in the icon's own place under the same parent and the same layout; a `UIAspectRatioConstraint` is still moved up onto the slot, where it goes on shaping that same `Size`. Only an `AutomaticSize` icon (still sizing itself from its own content, so its `Size` is not what it is showing) or a parent layout sorting by `Name` is refused. `restFootprint` — the AbsoluteSize-with-UIScales-divided-out helper — now serves only the text tier's `freezeText`, which runs at *gesture* time, the one moment a measurement is known to be real. A clipping ancestor refuses **only when it is tight around the icon** (under 1.5× the icon's box on an axis) *and* the grown icon would break out: a scroll window or panel body is many times the icon's size, and judging those would be judging the row's scroll position at clone time — a permanent bind decided by a transient offset, which leaves half a list animated and half not. Being under a rasterized group does **not** block it — scaling a descendant never changes the group's own `AbsoluteSize`. Audit attribute `UIMotionBound`, strongest result wins: `true` (button) > `"icon"` > `"text"` > `"fallback"` > `"no-target"`.
- **Text tier (ADR 0011 addendum, 2026-09-16)** — the tier between the icon tier and the fallback, for a button whose only visible content is one word (the Admin v3 custom-title `SaveButton`/`RemoveButton` are the reported case): `UIMotion.textTargetOf` returns that `TextLabel` and press/hover scale it with the icon tier's amounts (0.92 / 1.08), marker `"text"`. Claimed only when the lift is provably layout-neutral: button `AutomaticSize = None`, no `CanvasGroup` ancestor (ADR 0005), the button carries **its own** layout centring on **both** axes (exactly what `scaleTargetOf` refuses at `hasLayout(button)` — and what makes the label grow symmetrically instead of drifting off an alignment edge), exactly one visible `GuiObject` child which is that label (one level into a plain wrapper `Frame`, the same reach as `scaleTargetOf`'s `pick`), the button paints no image of its own (that is the icon tier's), and `labelAbsoluteSize × 1.08` still fits inside the button's *padded* inner rect — a label filling that rect keeps the fallback rather than spilling over the corner and stroke. **Residue trap:** a `UIScale` *on* an `AutomaticSize` element corrupts its own measurement (measured: rest 112 → 120.96 at 1.08 → 138.89 at 1.20, and **116.67, not 112**, after the `UIScale` was destroyed; an *ancestor* `UIScale` is clean), so an auto-sized target label is frozen for the gesture only — rest `AbsoluteSize` through `restFootprint` written as an offset `Size`, `AutomaticSize = None`, both handed back when the scale settles on rest and on the instant/teardown paths. Held per instance, so a press landing mid-hover thaws once; never left frozen, because these panels rewrite the labels' text per tab. The label is **never** reparented into a slot the way an icon is: kit code finds these labels with non-recursive `FindFirstChildWhichIsA("TextLabel")` (`AdminPanelV3UI.luau:215`).
- **Padding squash refuses a no-op (ADR 0011 addendum, 2026-09-16)** — the fallback's press insets the button's own `UIPadding`, but under a layout that centres on **both** axes that moves a non-filling child by exactly zero pixels (the content block is simply re-centred in the smaller inner rect). `squashPaddingOf` now refuses that shape — unless a visible child is sized in **scale** on an axis, which is measured from the inner rect and does shrink — before `slidePaddingOf` can create a padding for it, so `bindPressFallback` falls through to its brightness dip, which is visible.
- **Motion feel (ADR 0011 addendum, 2026-09-16)** — the durations and curves the vocabulary runs at, owner's brief: *"animasinya dibuat untuk dinikmati"*, smooth rather than brisk. Openings luxuriate — panel **0.32 s Quint Out + 0.20 s Sine Out settle** (0.52 s), dialog **0.24 + 0.15** (0.39 s, the same shape a touch quicker), centre `CENTER_OPEN_TIME` **0.40**, sidebar 0.38, toast 0.30, tab slide 0.38 Quint Out. Quart gave way to Quint on every travelling half: at these lengths Quart's tail reads as drift. **Every open/close pair keeps open > close** (0.52/0.22, 0.39/0.17, 0.40/0.24, 0.38/0.26, 0.30/0.22) and closes were softened by curve (`Cubic In` → `Quad In`, `Quart Out` → `Sine In`) rather than by time — a close that luxuriates is a door that will not shut. **The press-down is the deliberate exception at 0.08 s** (`PRESS_DOWN_TIME`, shared by the scale squash, the fallback padding inset and the fallback tint): the gap between a finger landing and the button reacting is read as input lag, not as elegance, and no grace afterwards buys it back. Everything after the contact is where the delight went — release 0.28 s Back Out, `MotionPresets.pressUp` 0.26 s Back Out. **Overshoot only on release, never on hover:** Back Out's overshoot is a fraction of the *travelled* distance and a press releases from a shallow squash (peaks ≈ 1.002 PressFeedback / 1.010 button tier / 1.006 icon+text tier — under a tenth of a pixel on a 16 px icon), the fallback's lands on internal `UIPadding` which cannot spill, and the icon slot plus `iconFits` already answer the clipping case; hover is 0.22 in / 0.18 out Sine Out with no bounce, because a cursor rests there and a bounce under a stationary pointer reads as a glitch. Row cascade `STAGGER_STEP` **0.055** with row fade 0.36 — the unchanged `STAGGER_MAX_ROWS = 12` cap bounds the worst case at `0.055 × 11 + 0.36 = 0.965 s`, so a 20-row list settles inside a second; the eight call sites that pass their own step keep it. `MOTION_SCALE` stays **1** and every duration still flows through `scaledTime`, so a buyer who set 0.8 still gets a proportionally brisker kit.
- **Shadowed motion defaults** — `CENTER_OPEN_TIME`, `CENTER_CLOSE_TIME` and `SIDEBAR_SPRING_FREQ` exist **twice**: as fallbacks in `Client/Utils/MotionPresets` and as live values in `Config.UIMotion`, which always wins. The spring proved it — the fallback said 6.2 while the config had shadowed it with 4.8 since the TopMenu spring landed, so the "default" was decorative. Change both, or the change is invisible and the explanation is wrong.
- **Reduced motion** — `GuiService.ReducedMotionEnabled` is honoured by every motion path (`UIMotion` snaps or skips; `AnimationHelper` and `PressFeedback` snap to their end state). Before ADR 0011 only the music panel read it. Corollary (ADR 0011 addendum, 2026-09-16): every release path ends at rest — reduced motion means no tween, not no final state. The setting is read-only from Luau, so it is verified by a manual Studio run with it on.
- **Open/close vs. life** — `AnimationHelper` still owns how a panel arrives and leaves (centre pop, panel/dialog travel, backdrop blur + zoom) with `MotionPresets` as the single source of durations and easing and `Config.UIMotion.MOTION_SCALE` scaling all of it; `UIMotion` owns what happens while the panel is open.
- **Progress leaderboards (2026-09-23)** — the Level and Streak boards rank from two OrderedDataStores, `LevelLeaderboard_v1` and `StreakLeaderboard_v1`, which only mirror values that live in `Overhead_v1` (still the source of truth). They are written by `ProgressLeaderboardRepository:observe` from the overhead payload each time it is synced to the player list; there is no backfill, so a player appears after their next join. Level score = level × `LEVEL_SCORE_SCALE` + xp within that level. Formatters take display units (the level number, not the score), because the client's podium counter re-reads the painted text. A streak only resets when its owner next logs in, so board builds check `lastLoginAt` for the top `STREAK_VERIFY_TOP` offline rows and drop broken ones. The couple board (`CoupleLeaderboard_v1`, key `<lowerId>_<higherId>`) ranks by when the pair was **first recorded**, not by when it formed: the kit has never stored a coupling date.
- **Weak tables are not a lifetime mechanism (ADR 0011 addendum, 2026-09-17)** — a `setmetatable({}, { __mode = "k" })` entry keyed by an Instance is dropped the moment no *Lua* value references that Instance, even while it is alive and parented (measured live: a parented `UIScale` in a weak set, ~40 frames of allocation churn → entry gone, instance still in the tree). The kit's one mechanism for state that must survive while an Instance lives is **`Shared/Utils/InstanceState`**: `InstanceState.new(init)` → `get` (never creates), `of` (creates on first use, connects exactly one `Destroying:Once`), `drop` (explicit reclaim). Only `Destroying` reclaims — never `AncestryChanged`, because pooled rows are detached and re-shown. Used by `UIMotion` (`MotionState`), `AnimationHelper`, `DonationLeaderboardController` (`Marks`), `WorkspaceLeaderboardRenderer`, `OverheadUI`, `UISoundHelper`, `CoupleController`, `ImageSwap`, `Main.client`. The `_fadeBases` maps passed to `UIMotion.captureBases`/`fadeIn`/`stagger` are plain strong tables owned by their panel (a weak one re-captures a mid-cascade transparency as the design). Weak keys are only for pure caches where a lost entry costs a recompute; the four that remain (`Music/Visuals.coverKeys`, `Music/LibraryView.shownBackground`, `CoupleController.cardTargetTransparency`, `AnimatorUtils`) say so in a comment. `UIMotionBound` has one writer: `UIMotion.markBound` (public; `PressFeedback` calls it).
- **Texture-budget guard** — `Client/Services/CanvasGroupBudgetService`: distance-culls Workspace `SurfaceGui`s that contain a rasterized group so their textures are released while nobody is near, keeping the budget free for ScreenGui panels (`Config.CanvasGroupBudget`; per-GUI opt-out attribute `ClubKitKeepSurfaceGui`).
- **Gaze follow (2026-09-20)** — the ACM's 3D avatar tracks the cursor with its head instead of spinning: `AvatarViewport3D:setGazeFollow(enabled, hitArea)`, opt-in per viewport, so only `AvatarContextUI` v1 asks for it and the donation panel and the profile tab keep the plain spin. While gaze owns a model **the auto-rotate is off** and the body is parked facing the camera (yaw π, the orientation `_positionCamera`'s camera on +Z looks at) — the owner's call, and it also removes the "gaze break" a clamped neck gives every time a spinning body turns its back. The angles come from the cursor's offset to the **viewport's** centre normalised by the **panel's** half-extent, clamped to `Config.AvatarContext.GAZE_YAW_LIMIT`/`GAZE_PITCH_LIMIT` (40°/25°) and eased with exponential damping (`GAZE_SMOOTHING`, rate per second); a cursor outside the panel eases back to centre rather than sticking at the clamp. Pointer devices only (`MouseEnabled and not TouchEnabled` — touch and gamepad keep the spin) and off under `UIMotion.reduced()`. Engine constants only; no `ClubKitConfig` key, and a rig with no neck joint falls back to the spin.
- **The Animator owns `Transform`; gaze writes the joint's rest (measured 2026-09-20)** — a modern rig's head joint is an **`AnimationConstraint`** (`Head.Neck`, with a `NeckBallSocket` beside it), not a `Motor6D`; R6 and older rigs still use `Motor6D` (`Torso.Neck`). Both expose `Transform`, and on both the `Animator` rewrites it every frame **inside a `ViewportFrame`'s `WorldModel`**: a `BindToRenderStep` write was overwritten at Input(100), Camera(200), Character+1(301), 500, Last(2000) and Last+100(2100) alike, and only stopping the idle track let it stick. What the Animator never touches is the joint's **rest offset** — `Motor6D.C0`, and for an `AnimationConstraint` its `Attachment0.CFrame` (the parent part's rig attachment, e.g. `UpperTorso.NeckRigAttachment`). Writing that composes on top of the idle animation, holds between frames (so gaze needs no priority games, only its own damped loop) and restores exactly. Rotate in the **parent part's** axes — `CFrame.new(base.Position) * CFrame.Angles(pitch, yaw, 0) * base.Rotation` — because R6's `Neck` C0 carries its own −90°/180° and joint-space angles read differently per rig. Head accessories follow for free (they weld to `Head`). Viewport-only: on a live, simulated character that same attachment also frames a `BallSocketConstraint`.

## Place packs

- **Place pack** — a per-owner add-on under `extras/place-packs/<Name>/` (rbxm + bridge Luau + README). Not engine: not in Rojo, not in Update Engine, not in the buyer changelog. Each pack is gated by a `ClubKitConfig.Features` flag so the engine and the pack never both run (`SyncBhms` ↔ `LegacySyncBhms`, `CinematicLoading` ↔ `LoadingScreen = false`, `Hierapolis` ↔ `HierapolisCustom`).
- **Config overlay** — a ModuleScript inside the buyer-owned `Hazastudio_ClubKitConfig` folder that `ConfigBootstrap` merges over the buyer config at boot when its `Features` flag is true (`HierapolisCustom` is the first). Lets a place pack change the role catalog / aliases / feature flags without ever rewriting `ClubKitConfig.luau` (ADR 0001 stays intact) and without living in the engine tree (Update Engine never touches it). Replace-wholesale for catalog sections, per-entry for `SystemRoles`, key-by-key for `Features`. Distinct from `ClubKitShowcase` (dev-only, engine tree, stripped on sync).
- **External loading contract** — the attribute handshake on `Players.LocalPlayer` between `Main.client` and a loading-screen pack (`Config.ClientBoot.*_ATTRIBUTE`): the kit publishes `ClubKitBootProgress` / `ClubKitBootSettled` / `ClubKitGameplayReady`; a pack sets `ClubKitExternalLoading = true` while its screen is up and the kit holds gameplay entry (join prompt, greetings) until it clears, bounded by `EXTERNAL_LOADING_TIMEOUT`.

## Roles & colors

- **Role color pair** — `roleColor = { primary, secondary }` on a role: `primary` is the chat name/tag color (must be unique per role), `secondary` an accent.
- **Role color stops** — optional `roleColor.stops` (2..5 hex strings): a multi-color gradient painted on the overhead **special-rank** text. Sanitized once at boot by `RoleColorDomain` (pure); when set, an omitted `primary`/`secondary` default to the first/last stop. `nil` = the nametag template's own gradient.

## Venue abuse (ADR 0008)

- **Backdoor** — code already inside a buyer place (free model, plugin, "admin" script) that `require`s a remote module or runs obfuscated payloads, giving outsiders server-side control. The most likely source of "a guest made everyone hear X".
- **Server-authoritative** — the kit's rule that a client request is only ever a *request*: every remote handler validates, permission-checks and rate-limits, and audio/effects come from templates already in the place. Client injection can therefore only affect the injector's own screen.
- **RuntimeGuard** — proposed `Server/Init` module watching *effects* rather than code: rogue `Sound`s (SoundGuard, boot-snapshot allowlist), runtime-created scripts (ScriptGuard), remote storms. Log-only first, beacons via `LicenseService.reportTamper("runtime:…")`.
- **Place security scan** — `tools/security/PlaceSecurityScan.luau`: static pass over every script in a place for `require(<id>)`, `getfenv`/`loadstring`, webhook tokens, unguarded remotes; run before publish and at delivery.
- **Foreign GUI (ADR 0012, 2026-09-16)** — a GUI that appeared in a player's `PlayerGui` *after* boot settled and is not in `StarterGui`, not in the boot snapshot, not one of the kit's own runtime GUIs, and not in the buyer's `AntiTamper.ForeignGuiAllowNames`. `Client/Services/ForeignGuiGuardService` names it and the `LocalScript`/`ModuleScript`/`Script` instances inside it; `Server/Init/TamperGuard` re-sanitises and beacons `foreign_gui:<name>`. **Log-only — there is no kick or brick path for this signal, by decision, not by default.** **Reach is `PlayerGui` only:** `game:GetService("CoreGui")` returns nil at LocalScript identity (measured 2026-09-16), so an executor window in CoreGui or a `gethui()` container is invisible and a quiet feed is not an all-clear. **Privacy:** the boot snapshot — the venue's own GUI inventory — never leaves the client; only post-boot additions are ever sent, and only their names. **Off in Studio:** the service returns before doing anything under `RunService:IsStudio()`, so playtests and plugin GUIs never beacon (ADR 0012 addendum 2026-09-17).
- **`ForeignGuiPolicy`** — `Shared/Domain`, pure: the caps (5 script names/GUI, 64 chars/name, 480 chars/detail, 3 GUIs per player, 8 per server) and the sanitiser both halves run. Backtick → `'`, `@` → `(at)`, control chars → space, non-ASCII → `?` — so a forged report cannot close the Discord code fence, ping the owner, or hide behind homoglyphs. The client applies it as a courtesy; the **server** re-applies it because the remote payload is hostile, and `apps/api` applies it again because a stolen secret can POST straight to `/v2/beacon`.

## External admin bridge

- **External admin** — a third-party moderation system (Adonis or Kohl's Admin) installed by the buyer. The Kit does not own it and does not fork it.
- **Facade** — the engine-side `ExternalAdminFacade` singleton: a stable API surface that external admin plugins/addons call to run Club Kit actions (`setRole`, `announce`, etc.).
- **Provider** — `ClubKitConfig.ExternalAdmin.Provider` value (`"Adonis"`, `"Kohls"`, `"None"`); runtime gate only.
- **Rank sync** — one-way mirroring of Club Kit staff role changes into the chosen external admin's ranks, driven by the `Gift:RoleChanged` event.

## Self-service custom title

- **Custom Title panel** — the buyer-place ScreenGui `1000-01-CT-ADDON` (kept under that name deliberately, outside the `NN-Name` kit convention): a draggable `CustomTitleModal` plus two pickers (`SelectPresetModal`, `SelectTypefraceModal`) that let a **player** edit their own overhead title's text, size, color preset and typeface. Replaces the text-only universal modal that the profile "Title" row opened. GUI ships as RBXM/manual, never source-sync.
- **Title gate** — a player may open the panel when `overhead.level >= ClubKitConfig` threshold, **or** when they already hold an admin-granted `specialTitle` (preserves the pre-existing `canEditSpecialTitle = specialTitle ~= nil` rule, so migrated title holders never lose access). Threshold, quota count and window are buyer-tunable via schema fill-forward, not engine constants.
- **Title quota** — rolling window (default 5 changes / 7 days) stored as a timestamp list on `Overhead_v1`, not a new DataStore key. One `Update Title` press that changes *anything* (text, size, preset, or font) costs one slot; `Remove Custom Title` is always free, but setting a title again afterwards costs a slot. Because `OverheadDomain.sanitize` is a whitelist rebuild, the field only survives a load if added to `Types.OverheadStoredData`, `defaultStoredData()` **and** `sanitize()` together.
- **Title catalog** — players get the same catalog as admins: all `AnimationModes.PRESET_MODES` presets and `Config.Admin.TITLE_FONTS` fonts, sizes from `TITLE_SIZE_ORDER`. No player-only whitelist, no tier gating.

## Admin Panel v3 & image titles

- **Admin Panel v3** — the ScreenGui `04-AdminPanelv3`, replacing `04-AdminPanelv2` as the admin custom-title surface. Same inner ref names as v2 (`SelectedPlayerInfo`, `02-SearchBox`, `PlayerSelectorCard`, `SelectSize`, `02-InputCustomTitle`, `OverlayWrapper`/`SaveButton`) but every outer container was renamed (`01-HeaderWrapper`→`Header`, `02-MainContentWrapper`→`MainContent`, `1-SelectPlayerFrame`→`SelectPlayerFrame`, `2-InputTitle`→`CustomTitleWrapper`, `01-ScrollingFrame`→`CustomTitleTab`), so the v2 binder cannot be pointed at it — its `WaitForChild` calls carry no timeout and would yield forever. Carries **its own copies** of the preset and typeface pickers rather than borrowing the player addon's, so the admin panel never depends on `1000-01-CT-ADDON` being installed. The emoji picker is **dropped** in v3; admins type emoji straight into the field.
- **Image title** — an *additional* overhead layer, not a replacement for the text title. Lives in `OverheadGUIMainTemplateV5` as the row `02-AddOnCustomImageBadge` → `ChangeableImage`. The wrapper's `UIListLayout` sorts by **Name** (V4 does too), so the `02-` prefix is what places it directly under `01-SpecialTitle` and above `02-BadgeGroup`. The row is deliberately wider than a 20:9 image and letterboxes it — that is the intended look, not a bug to fix. The row ships `Visible = true` with a placeholder asset, so the renderer must hide it whenever the player has no image title.
- **Six places an overhead field must be registered** — adding a field to `Overhead_v1` is never one edit. Four are whitelist rebuilds that silently drop unknown keys (`Types.OverheadStoredData`, `OverheadDomain.defaultStoredData`, `.sanitize`, `.applyHardcoded`) and two are explicit field lists that decide whether a change is even *noticed*: `OverheadService.computeInputsFingerprint` (the S1 short-circuit — if it does not change, `buildPayload` is skipped entirely) and `OverheadController.fingerprintPayload` (the delta broadcast — a field missing here is never sent to the client). A server mutation should also call `overheadController:invalidateBuildCache(userId)` before `refreshPlayer`, the way the couple flow does; the inputs fingerprint is only as good as the cache entry it reads, so without the bust a refresh can be short-circuited and the overhead keeps the old value.
- **Overhead GUI variant** — `Config.OverheadGuiVariants` keyed by `Config.Overhead.GUI_TYPE`; a variant is `{templateName, renderer, wrapperName, preserveLayoutOrder}`. `renderer` is inert metadata (stored on `OverheadUI` but never branched on) — rendering is driven by row names — so adding V5 is a config entry plus code for the new row, not a new renderer.
- **Image reuse registry** — every image asset ever assigned as a title in this place, kept in one **place-global list under its own versioned DataStore key**, so an admin can re-pick an image without retyping the id. Distinct from a config catalog: it grows from use, not from the buyer's config.

## Overhead layer visibility (ADR 0009)

- **Wearer side vs viewer side** — two independent systems, easy to confuse. `publicOverheadLayerVisible` / `publicOverheadBadgeVisible` on `Overhead_v1` are the **wearer's** state: what everyone else sees on your nametag, and what Settings → *Name Tag Details* writes through the server. The client attributes `SettingsOverheadLayerVisible_*` / `SettingsOverheadBadgeVisible_*` only filter the viewer's **own** head, as instant feedback before the server has mirrored the change; they must never filter other players' nametags.
- **Default vs hard-off** — `ClubKitConfig.Overhead.DefaultLayers` / `DefaultBadges` carry three values per key. `true` / `false` are **defaults**: they seed a player's *first* stored record, so a changed default never reaches back to existing players, and Settings can switch the layer on again. `"off"` (also `"disabled"`, case and spaces forgiven) is a **hard-off**: enforced on every payload build and every render, so it reaches players whose record predates the change, and its Settings row is hidden. Nothing stored is rewritten, so deleting the `"off"` restores every player exactly as they had it.
- **Hard-off wins over kit overrides** — four paths force a layer visible on the wearer's stored data: an admin granting a title (`AdminController` → `SpecialTitle`) and a couple forming (`CoupleDomain.applyCouple`, `OverheadController`, and the client `SettingsController`'s relationship patch → `CoupleName`). Each asks `OverheadDomain.isLayerDisabled` first, so none of them can punch through a hard-off or bank a dead `true`.
- **OverheadLayerPolicy** — the pure tri-state reader (`classify`, `defaultVisible`, `disabledSet`, `isDisabled`, `enforce`, `invalidValueKeys`). No Roblox globals and no `Config` require, so it is lune-testable and safe on both sides. `ConfigBootstrap` projects the buyer's table into `Config.Overhead.DEFAULT_*_VISIBLE` (booleans, what seeds a record) **plus** `DISABLED_LAYERS` / `DISABLED_BADGES` (the hard-off sets), filling those two **in place** so a captured reference stays valid — and before `table.freeze(Config)`. Everything downstream reads them at call time, never at module load, because `ConfigBootstrap` runs after the domains have loaded.
- **Empty section hides itself** — `SettingsTabBinder:updateConditionalRowVisibility` already hides a settings section whose rows are all invisible, so switching every layer off takes the *Name Tag Details* heading with it. The same routine hides a per-badge row when the `BadgeGroup` layer itself is hard-off, since no badge toggle could show anything.

## Graphics presets

- **Graphics preset** — the player's `Low` / `Balanced` / `High` choice (`GraphicsQuality` bundles, applied client-side by `SettingsController`). Visual Comfort toggles (`Shadows`, `Textures`, `Background Blur`, `Hide All Particles`) are per-field **overrides** on top of the preset. **High** = the map as built. **Balanced** = sun shadows kept, every local light's shadows off (club lights are the costliest casters). **Low** = Shadows Off (zero shadows) with the map's textures and `SurfaceAppearance` kept as built — only the `Textures` toggle detaches `SurfaceAppearance`.
- **Default preset** — the preset a player starts on when they have **no saved settings record**, and what Settings → Reset returns to. Buyer: `ClubKitConfig.Graphics.DefaultPreset`, kit default `"Low"`. A default, not a force: the kit saves the whole Settings panel on any change, so anyone who ever touched Settings keeps their stored preset.
- **WorldGraphicsService** — the single owner of `BasePart.CastShadow`, light `Shadows` and `SurfaceAppearance` parenting for the whole Workspace. No other kit code writes those properties; the tag-gated passes in `SettingsController` keep only textures/materials and light `Range`.
- **Mesh detail is place data, not a preset knob** (settled by measurement 2026-09-12). `MeshPart.RenderFidelity` **cannot be changed at run-time**: the engine warns `Cannot change SolidModel RenderFidelity during Run-Time` on every write and the renderer keeps the mesh it tessellated at load — the property value changes, so a census of it looks like success while nothing visible happens. A venue shipping most meshes at `Performance` (lowest detail at every distance) is the biggest single reason a High preset can still look flat, and the only fix is authoring the meshes in Studio and saving, exactly like `Lighting.Technology`. `GraphicsBundle` carries a comment where a `meshFidelity` field briefly lived; do not re-add it. **Census meshes in Edit mode, never in a playtest** — StreamingEnabled means a playtest sees a subset (810–1352 of PARKLAB's true 3365).
- **High pushes quality up only where the platform allows it** (owner 2026-09-12, "bener-bener high tanpa kompromi"). Every preset otherwise only *restores* what the builder set, which is why High used to be a no-op tier. What is left after the mesh finding: it declares its own shadow tier (`shadowQuality = "High"`, softness 0.55) and holds it across a Shadows toggle round-trip.
- **Quality knobs only — High never overrides artistic intent.** It does not switch on a `Bloom` the builder disabled, does not force `CastShadow` on a part left non-casting, and does not raise `EnvironmentDiffuse/SpecularScale` above the map's own values. Those would change how the venue *looks*, which is not the same thing as rendering it at higher fidelity.
- **The player's own Roblox slider is the real ceiling.** `UserGameSettings.SavedQualityLevel` caps everything: at `QualityLevel1` the High preset still renders at the client's lowest quality. The kit **reads** it and suggests raising it once per session (`Config.Graphics.SUGGEST_QUALITY_BELOW_LEVEL`, default 8); it never writes it, because that setting is account-wide and follows the player into other experiences. `Automatic` (enum value 0) never triggers the notice — the engine is already choosing per device.
- **`Lighting.Technology` is out of reach.** It is `ReadOnly`/`RobloxScriptSecurity` and documented "non-scriptable, only modifiable in Studio", so no kit code can read *or* set it. On `Voxel` there are no shadow maps at all and `Lighting.ShadowSoftness` — which High sets to 0.55 — does nothing. Switching a place to `Future` is a manual, place-data decision for the buyer.
- **Phone clamp** — High forces Precise on every mesh, which a phone cannot carry, so a phone player who picked High *renders* at `Config.Graphics.PHONE_MAX_PRESET` (Balanced). Their stored choice is never rewritten: back on desktop they get High again. Resolved in `GraphicsQuality.clampPresetForDevice`, applied in `refreshEffectiveGraphics`, so it is the rendered preset that is clamped, not the saved one.
- **Shadows toggle is three-valued, not two.** The Settings row stores `"Balanced"` when switched on whatever preset you are on, so keying shadow fidelity off that stored word silently downgraded a High player to Balanced's softness with no way back short of re-picking the preset. Turning shadows back on now restores the **preset's own** fidelity, and the row honours a `onValues` list (`{"Balanced", "High"}`) so it does not read OFF on the preset with the best shadows.
- **Shadows Off** — effective `shadowQuality == "Off"`, reached via the Low preset or the `Shadows` toggle. Means **zero shadows on screen, not fewer**: `Lighting.GlobalShadows = false` **and** every `PointLight`/`SpotLight`/`SurfaceLight` `Shadows = false` **and** every `BasePart.CastShadow = false` — across the whole Workspace, avatars included, and kept true for instances that appear later (StreamingEnabled, GLights fixtures that build their lights on the client at runtime). Turning shadows back on restores each instance's own original value, never a blanket `true`. Opt-in `ScalableGeometry`/`ScalableVfx` tags do not gate this — a buyer who never tagged their map still gets zero.
- **SettingsController register ceiling** — the controller's inner setup closure holds ~166 locals (the `count-locals.ps1` top-level count of 49 does not see it; `rg -c '^\tlocal '` on the file is the closer measure), against ADR 0002's freeze line of 170. The 2026-09-12 graphics work spent two of the remaining few (`suggestedQualityBump`, `maybeSuggestQualityBump`). Treat the closure as effectively full: further graphics logic belongs in `WorldGraphicsService` or its own module, never as more `local function`s there.

## Profile likes

- **Daily like** — with `ClubKitConfig.AvatarContext.DailyLikeReset` (default true), a player may like each other player **once per WIB day**, and every one of those likes is **+1 to the target's lifetime total**. Off, the pre-2.12 rule applies: one standing like per person, ever, with an Unlike button. The day boundary is `StreakDomain.toDayNumber` — the same "today" the daily streak and the daily donation window use.
- **One number per (target, giver)** — the stored entry is `nil` (never), `0` (legacy unliked), `1` (legacy standing like), or a **WIB day number** ≥ `AvatarLikePolicy.MIN_DAY_STAMP` (10000 = 1997). That threshold is what lets daily mode ship with **no DataStore key change and no migration**: a real day stamp is ~20,700 and can never be mistaken for a legacy `0`/`1`, and a shard does not grow when the same people like every day.
- **A legacy like is spent, not today's** — a standing like from before the change reads as "liked on a day nobody recorded", so its holder may like again today. The other reading would lock every existing liker out for a day that never happened.
- **`likeTotal` vs `activeCount`** — `activeCount` counts people *holding* a like; `likeTotal` counts likes *given*. A target's total is rebuilt from `likeTotal` (`reconcileSummary`), because once one person can like daily the two stop being the same number. A shard written before 2.12 has no `likeTotal` and falls back to its holder count, which is exactly what its total was.
- **One-way per day** — the client stops offering Unlike in daily mode and the server refuses it, so a crafted remote cannot spend the day's like and then take the count back down. The button reads `Config.AvatarContext.LIKE_LABEL_DONE_TODAY` while today's like is spent.
- **`daily_like`** — the transition for a repeat like on a later day. It earns the "X liked your profile" notification and the flying hearts, exactly like `first_like`; `reliked` deliberately does not, so the old toggle can never become a notification-spam route.

Place data, never source-sync.

On V2 the binders **follow the designer's values** (template UIScale, `CountDownBar` width, `TextSize`, stroke colour); on V1 those stay as they were, so a buyer who never installs the new GUI sees no change. A V2 GUI left at `DisplayOrder` 0 is lifted to `Config.NotificationCenter.V2_DISPLAY_ORDER` (300).

## Creator live status

- **Creator** — a Roblox player the venue owner has registered in the clubkit-infra dashboard against a TikTok handle. Not something a player can claim for themselves.
- **Live status** — whether a creator is live on TikTok right now, as determined **by the VPS** checking the handle's public TikTok profile; the game only ever learns "userId X is live", never the handle. Shown as a generic `🔴 LIVE` on the creator's overhead plus a general notification.
- **Two policy lines, deliberately split (owner, 2026-09-11).** *Roblox side — hard line:* the experience **never names the platform and never shows a handle or link**. Community Standards forbid displaying external services / off-platform identifiers in an experience, and `PolicyService.AllowedExternalLinkReferences` is a legacy field that always returns empty, so there is no compliant way to allow it; breaking this puts every buyer's game at moderation risk. Do not "improve" the badge by adding the platform name. *TikTok side — accepted grey:* TikTok has no official "is live" endpoint, so detection scrapes public profile state from the VPS. That risk (blocking, breakage when TikTok changes its pages) lands on the VPS and on feature reliability, not on buyers' Roblox experiences. The clean alternative — the creator's streaming software (OBS) signalling the VPS — was offered and not chosen because it misses phone streams.

## Music library modes

- **Music library mode** — buyer choice of how the shared music library relates to DataStore, via `ClubKitConfig.Features.MusicReadOnlyLibrary` (boolean). Two values:
- **Editable** — the legacy behavior and default (`false`): DataStore read at boot + writes persist, catalog seed, sync poll, Manage tab shown for permitted ranks.
- **ReadOnly** — (`true`) no DataStore at all: library comes from the MusicCatalog script + in-game requests held in memory (lost on restart); legacy stored data is untouched but not shown; Manage tab hidden. The DJ tab and live control follow `musicControl`, not the manage gate, so they stay available (changed 2026-09-13 with the privilege split — before it, the shared gate hid the DJ tab too).
- **Web** — (`Features.MusicWebLibrary = true`, ADR 0010) the library is fetched from the VPS and `MusicLibrary_v1` is demoted to a read-through cache. The game never writes the library; editing happens only in the customer area. Opt-in in 2.13; from 3.0 the only mode, and the flag itself is retired.
- **Web snapshot** — one well-formed answer from `GET /game/<key>/v3/music/library`, identified by its `revision` (the ETag). It **replaces** the in-memory library and overwrites the DataStore cache wholesale; it is never merged. Nothing else replaces the library: a licence 403, 503, outage, malformed body or an empty web library beside a non-empty cache all mean "keep what is playing" (`MusicWebLibraryPolicy`).
- **Library import** — the one-time transfer of a venue's DataStore library into the web, done by the kit itself on the first boot in web mode (ADR 0010 addendum). Merged per entry, never replacing; recorded per game so it happens once. Until it lands, pull answers carry `import_required` and the kit applies no snapshot. Not "migration from empty": a web library can be complete-looking and stale at the same time.
- **Carried track** — the song on air when a snapshot removes it. It stays in memory, in no playlist, until it stops playing, because the session skips the moment its current track is missing from the repository.
- **3.0 (owner, 2026-09-14):** Web is the only mode, for every venue. Editable and ReadOnly retire together with the Manage tab. `MusicCatalogSeed`, `MusicReadOnlyLibrary` **and `MusicWebLibrary`** are ignored and listed in `ClubKitConfigSchema.RETIRED_KEYS`: never filled forward, not offered in the plugin, left untouched in a buyer file that still has them, and named once in the boot log. `MusicWebLibrary` retires instead of defaulting to `true` because 2.13's config patch writes `MusicWebLibrary = false` into buyer files, so a new default would never reach them. A venue without the VPS configured plays its DataStore cache. The buyer's `MusicCatalog.luau` is left untouched but no longer read — anything it ever seeded is already in the DataStore library the import carries to the web.
- **Play-once request** — what Request From ID means from 3.0 (owner, 2026-09-14): a pasted Roblox audio asset ID goes into the queue for one play and is never written to the library. Before 3.0 the same button created a library track, which is why it had to be hidden in Web mode. **Open to every player** (owner, 2026-09-14), not gated by `musicControl`, with limits of its own rather than the normal request limits (which are 100 per 30 s and 100 queue slots): one waiting play-once track per player, three requests per ten minutes. Holders of `musicControl` are exempt from both limits (owner, 2026-09-14). A buyer switch `Music.PlayOnceRequest` (`"everyone"` default / `"control"` / `"off"`) lets a venue lock it down without waiting for a kit update. The server still refuses anything that is not an Audio asset; it cannot judge what the audio contains, so that moderation risk sits with the venue.
- **Music volume scale (owner, 2026-09-16)** — the Settings "Music Volume" slider is a **0–100% scale, unchanged and still stored as 0–100**; what changed is what a percentage *means*. The percentage is multiplied by `ClubKitConfig.Music.MaxVolume` (kit `Config.Music.MAX_VOLUME`, default **4**, clamped to Roblox's 0–10 `Sound.Volume` range by `ConfigBootstrap`) to get the `Sound.Volume` the player writes: 100% = 4.0, 25% = 1.0. Before this, 100% was 1.0. The owner asked for the remap knowing it makes every venue four times louder for every existing player without anyone touching a slider — *"yang sekarang terlalu kecil"* — so this is deliberately a **venue-level loudness change**, not only a wider per-player choice. Nothing in the DataStore record moves: `SettingsDomain.sanitizeStored` still validates `musicVolume` at `0, 100`, and the `_musicVolBase` one-shot that rewrites an untouched `50` to `100` is untouched. The scaling lives in exactly one place — `SettingsController`'s `SettingsMusicVolume` player attribute, which now carries an already-scaled `Sound.Volume` rather than a 0–1 factor — and `MusicPlayerController` clamps every write to `0, MAX_VOLUME`. **Above 1.0 Roblox amplifies, and amplification clips**: a loud master under a boosted DJ equalizer band distorts audibly, which is what `MaxVolume` is there to lower.

- **Link ingest** — adding a track in the customer area from a link instead of a file (brm-api `POST /uploads/youtube`, a name kept for the dashboard). From 2026-09-22 it takes one YouTube video **or one SoundCloud track** (`youtube/link-source.ts`; playlists, sets, profiles and SoundCloud Go+ 30-second previews are refused with a reason). The title comes from the link unless typed, and the **cover** too (below).
- **Long set** — a track up to **3 hours** of in-game play time (owner, 2026-09-22: mixtapes in a club map). The limit is checked on the source length, because that is what plays: the compatibility routes speed the file up and the kit plays it back at the matching `normalSpeed`. Split into 7-minute parts, so up to **26 parts** (`Config.Music.MAX_TRACK_PARTS`, `MusicDomain.validateTrack`, brm-api `MAX_TRACK_PARTS` — three copies of one number). A kit before 3.0 drops a longer track whole when it pulls the web library, and plays it (loading every part at once) when it reads the auto-synced DataStore.
- **Part durations** — `track.partDurations`, the raw seconds of each part's asset (before playback speed), sent by brm-api from its ffprobe of the parts. Optional: kept only when there is one positive number per part. The client uses it instead of loading every part to measure it; a part's own `TimeLength` replaces its entry once it loads. All clients read the same numbers, so they stay in step with each other even where a number is a fraction of a second off.
- **Drawn cover** (ADR 0014) — the cover the kit draws for a track without its own image: mesh artwork (`CoverMesh`, seeded by `name — creator`) + cover text in a **cover layout** (chosen per playlist on the web: tab Template; tabs Gradien/Gambar = layout `"none"`, the playlist's own cover for the card and every song). Nothing is uploaded, and a place holds no cover settings: brm-api sends each track's resolved **`cover`** (layout, lines, kicker, corner **mark**). Render mode: UIGradient layers always, EditableImage on top only where the owner is verified and enabled it.
- **Cover text** — the lines on a drawn cover, written by brm-api's rules (`library/cover-text.ts`) in two **headline modes** (`playlist`: playlist name ≤10 chars, default; `title`: song title ≤26) — the venue picks one on the web, next to the **mark** (`""` = experience name, `"-"` = none); lines editable per track, flags = "Perlu dicek". The kit only fills in the experience's name, swaps a subline equal to the mark, and clips the ticket to 10.
- ~~**Link cover**~~ (off since 2026-09-22, see Drawn cover) — the link's thumbnail, centre-cropped to a 512 px square and uploaded as a Roblox **Image** asset (not a Decal — a Decal id shows nothing in an `ImageLabel`) with the venue's Open Cloud key, then stored as the track's `coverImageAssetId`. Best effort: any failure leaves the track on its playlist's cover. A new image goes through Roblox moderation, and the cover is blank in game until it is approved. The library item's own value wins over the queue's, `""` (cleared by the customer) included.

## Music roles & tiers (ADR 0010)

- **`musicManage`** — the privilege to edit the library (playlists, tracks, DJs). Under the Web mode it is a *web* permission; the in-game privilege of the same name is retired.
- **`musicControl`** — the privilege for live control during an event: DJ mode, effects, playback speed, soundboard, admin skip, and the transport row of `06-MusicPlayerGUIv3` (previous, rewind, play/pause, seek, clear queue — owner, 2026-09-13). Stays in-game, held by the DJ role. Split out of `musicManage`, which used to gate both. Players without it see only Vote Skip. **Inheritance:** a buyer config that does not write `musicControl` (every config from before the split) gets the role's *effective* `musicManage` — after role-level `privileges` overrides are merged — resolved in `RoleCategoryBuilder.build` at boot, so no buyer file is patched (ADR 0001). An explicit `musicControl` anywhere, category or role, wins over the inference.
- **DJ** — an entry in the venue's roster: a **stage name** (what tracks carry as their creator) tied to **exactly one Roblox account** (owner, 2026-09-22, reversing the earlier "a DJ may be an outside artist who never joins"). Linked on the web (brm-api `creators.roblox_user_id`, migration 0016; one account per DJ per venue), and **required for every DJ**: an unlinked name — every DJ from before the change, and names that exist only because a track carries them — shows "Belum ditautkan" and cannot be picked for a track until linked. The stage name stays the DJ's own and does not follow the account's display name. The game pull carries the roster as **`djs: [{ name, userId }]`**; the kit is meant to give those accounts the venue's **DJ role** (musicControl + tag + tools, via the existing role setup) and show their avatar on DJ Set cards — **kit side not built yet** (3.0). Still not the same thing as a [Creator](#creator-live-status) (the TikTok live-status entity).
- **DJ Set** — a Library card in `06-MusicPlayerGUIv3`: one per DJ, listing every track whose creator is that DJ. Derived at read time, not stored (owner, 2026-09-13). Grouping is by creator name, so renaming a DJ in the dashboard (which does not rewrite existing tracks' artist) splits the set.
- **Private playlist** — a playlist with `visibility = "private"`. In-game it is openable and playable only by holders of `musicControl` (a DJ's stock); everyone else sees its card and gets the `PrivateWall` in `06-MusicPlayerGUIv3` (owner, 2026-09-13). The server sends that card without track ids, and leaves the playlist's tracks out of every list a non-holder can ask for (all tracks, favourites, new drops) — so DJ Sets, derived from all tracks, cannot leak them. Previously gated by the in-game manage privilege, which ADR 0010 retires. **Set in the dashboard** (Edit playlist → Akses di game), stored in brm-api `playlists.visibility` (owner, 2026-09-15). That column is `NULL` until the web sets it — meaning "not decided here", served to the game as no key (which the kit reads as public) — so the one-time import and the legacy merge keep a game's own `private` instead of overwriting it with a default.
- **Playlist cover** — what a Library card and Now Playing show for a playlist: either one of the kit's **8 fixed gradients** (`coverType = "gradient"`, `coverValue` 1–8, `Config.Music.COVER_GRADIENTS`) or a Roblox **Image** asset (`coverType = "image"`). There is no free colour: the dashboard offers exactly those 8 (owner, 2026-09-15), and the old hex `playlists.color` no longer reaches the game. A **Decal** id is refused, because the kit's large cover (`rbxassetid://`) shows a Decal blank even though list thumbnails (`rbxthumb://`) render it. **Track cover override** (owner, 2026-09-15, reversing the same day's "playlist only"): a track may carry its own **Image** cover, set in the dashboard's Edit track; without one it shows its playlist's cover. Image only — there is no per-track gradient. DJ Set and New Drops cards take their first track's cover, so they show that image too.
- **Free tier** — managing the library by pointing at Roblox audio assets that already exist. Needs no Open Cloud key, so it is open to every buyer. From 3.0 the dashboard Musik page opens for every venue; `games.music_enabled` gates only the Studio / BRM tier (owner, 2026-09-14). A venue's page opens by itself once its game reports kit 3.0 or newer through the licence check; before that the page explains that the update comes first.
- **Studio / BRM tier** — uploading audio or importing from YouTube. Needs the buyer's own Open Cloud key and VPS transcode time; stays a paid add-on.
- **Bypass recipe** — the pitch/tempo shift BRM applies before upload, undone at playback by the track's `playbackSpeed`. A track that did *not* go through a recipe plays at `1.0`; see ADR 0010 on why `nil` is not a safe way to say "normal".
- **Music player GUI v3** — the redesigned `06-MusicPlayerGUIv3` (currently a mock in StarterGui of the test place). Three tabs: Now Playing (with a separate DJ-on-stage view and a transport row), Library (playlist list → one playlist's detail page, with DJ Sets, Liked Tracks, `PrivateWall`, Request From ID), DJ. No Manage tab, no track/playlist forms, no add-to-queue confirmation. "Liked Tracks" is the existing favourites (`MusicFavorites_v1`), renamed on screen only. **Release (owner, 2026-09-13):** v3 replaces v2 outright in 3.0 under the name `06-MusicPlayerGUI`, shipped by RBXM; the two do not coexist.
- **`GuiRefs`** — `Client/UI/Music/GuiRefs` resolves the v3 GUI's elements once at bind. It is strict on missing or wrong-class names (asserts) and *loud but tolerant* on duplicated names (one `warn` per parent + name, first match returned) — a buyer GUI with a pasted-twice template keeps working and tells the owner which element to delete.
- **Playlist cover stack (2026-09-16)** — the two decorative frames behind the detail cover, `LibraryTab…2-SelectSong.TrackListLeft.Wrapper.BackdropNear` / `.BackdropFar`, now mean something: each holds a `CoverImage` that `LibraryView` paints, so the detail cover reads as the top of a stack of albums. The art is **two distinct image covers taken from the opened set's own tracks**, picked from a hash of the set's id rather than with `math.random` (the detail repaints on most store changes and a re-roll would flicker the art), falling back to the set's own cover for any slot it cannot fill — a set with no image-covered tracks shows the same art three times, which is still a stack. Opening a different set collapses both frames onto the front cover's plane and fans them back out, back layer last; the plane is extrapolated from the two frames' own designed offsets (the Far→Near step applied once more), so no buyer template has to lay the cover out the way this place does. **The frames are GUI-template decoration, not kit-created:** every lookup is a `FindFirstChild` that degrades silently, so a place without them keeps exactly the panel it has today — which means shipping the visual to other buyers needs the GUI packed (RBXM / manual surface), not just a source sync. `NowPlayingTab…QueueListTemplate.Wrapper` has the same pair and is deliberately untouched.

## Donation world effects (ADR 0013)

- **`WorldEffects`** — `ReplicatedStorage.WorldEffects`, the four donation VFX models (`Smite3`, `Smite4`, `BlackHole`, `Nuke`). **Not in the repo**: `default.project.json` maps `src/ReplicatedStorage` and this folder is not under it, so the models live only in the place and the packaged `.rbxm`. The practical rule that follows: *a change to the model cannot ride a source-sync release* — only code reaches existing buyers, so anything that must reach them has to act on the `:Clone()` at runtime. A third-party pack, not ours: 138 unique assets from 65 creators, one of which (`93040740783271`, the giant's animation) is `hazatargz`'s; see [`docs/audits/ASSET_OWNERSHIP_AUDIT.md`](docs/audits/ASSET_OWNERSHIP_AUDIT.md).
- **Effect name** — the string in a `WorldEffectTiers` row (`Nuke` / `Smite4` / `BlackHole`), which is both the model to clone and the key a theme is chosen by. `Smite3` is a valid name that **no shipped config ever reaches** — the default tiers are 100k→`Nuke`, 250k→`Smite4`, 500k+→`BlackHole` — so GreenHammer has never run at a buyer.
- **Theme role** — one of the **21** colour groups that partition `Smite3`'s 73 coloured nodes, derived from the *pair* (Smite3 colour, Smite4 colour) rather than from either colour alone. Needed because `Smite4` is hand-painted, not hue-rotated: the shift ranges +135°..+300° and one source colour lands on three different targets. Because the roles are how the pack's author actually grouped the work, a palette per role reproduces **both** looks exactly. Three roles are identity; one node (`DiamondHammer/Effects/Trails/HandleTrail`) has a 5-keypoint gradient and is painted per keypoint. The map is generated data checked into the repo, because `Smite3` is pruned at runtime and the mapping cannot be re-derived afterwards.
- **`Donation.EffectTheme`** — `{ Default, ByEffect }`. Keyed by **effect name, never by tier row**: `WorldEffectTiers` is in `ClubKitConfigSchema.ARRAY_REPLACE_KEYS`, so a buyer who has that array (the template ships one) gets theirs used wholesale and any new field inside a tier row would reach nobody, silently. `Default` is the venue-wide palette; `ByEffect` keeps tiers visually distinct so a 500k donation still reads as bigger than a 250k one.
- **Fill-forward reaches nested keys** — `ClubKitConfigSchema.fillForward` recurses into nested tables and fills any key missing from the buyer's file. The rule is "the key must exist in the schema defaults", *not* "the key must be top-level". (Corrects an earlier note in `docs/buyers/night-zone.md`: `Donation.ReliabilityV2` had to be inserted by hand because it was absent from the schema at that version, not because it was nested.)
- **Resolving is not playing** — an asset that `MarketplaceService:GetProductInfo` returns happily can still be unplayable in game. `SoundAssetSanitizer` already blocks `9009370950` as "file not found" while `GetProductInfo` resolves it normally. Sweeping ids for existence proves nothing about runtime; only playing them does.
